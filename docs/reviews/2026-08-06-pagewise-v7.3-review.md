# 7.3 评估：7.2 的头号修复覆盖不到它自己举的例子

> 复核更正：V88（页码不可点）不成立，功能早已存在且测试齐全，已在 §2.1 撤回并说明原因。

日期：2026-08-06 ｜ 基线：7.2.0（已发布）
实测编号接续 `2026-08-06-pagewise-v7.2-review.md`（V1–V83）。

---

## 0. 结论

这一轮最重要的三条都是**针对上一版的更正**，不是新功能：

1. **7.2 的按页去重漏了 `read_pdf_page`。** 上一版评估举的例子是「`read_pdf_range(10,20)` 之后再 `read_pdf_page(14)`」——而 `read_pdf_page` 既不查也不写那个已读集合，所以**那个例子本身没被修好**。四种先后组合里只有一种真正生效。
2. **7.1 的「索引工具退休」很可能是净亏。** 运行中途改 `activeTools` 会改掉工具块，而工具块在缓存前缀里排在消息前面——省下一个工具的 schema，代价是这一轮剩下的每一步都拿不到缓存价。
3. **搜索工具的参数说明写着 "default 50"，实际是 12。** 7.1 改了默认值没改描述。这是提示词里的一句假话，模型据此决策。

第 2 条（会话）我原本提的是「答案里的页码不能点」，**复核后撤回：这个功能早就有，而且做得比我打算提的方案更细。** 我只查了一个文件就断言它不存在——和 V84 是同一种错误，只是方向相反。会话轴的内容因此换成键盘走对话。

## 1. token · V84–V87

### 1.1 按页去重覆盖不到最常用的读取工具 · V84

```
agent.ts:435,445  budget.delivered 的读与写 —— 全部在 readPageRange() 内
readPageRange 的调用者：read_pdf_range(870)、read_section(938)
read_pdf_page(692-817)：grep delivered → 0 处
```

`read_pdf_page` 自己走 `readPageText` + 切片，完全绕开 `readPageRange`。于是：

| 先读 | 后读 | 去重生效？ |
|---|---|---|
| range / section | range / section | ✅ |
| range / section | **page** | ❌ 全文再发一遍 |
| **page** | range / section | ❌（page 从未登记，range 查不到） |
| **page** | **page** | ❌ |

四种组合只有一种生效，而没生效的三种都涉及**单页读取——最常被调用的那个工具**。上一版 CHANGELOG 写的「同一页不再被买两次」，在最典型的路径上不成立。

→ 修法：把去重下沉到 `readPageText` 的调用点，或让 `read_pdf_page` 走同一条登记路径。**这是 7.3 必须做的第一条。**

### 1.2 运行中途退休索引工具，很可能是净亏 · V85

```
prepareStep:  surveyed → activeTools = 六个工具去掉 document_outline
系统提示           2,049 字符 ≈ 512 token
工具描述 + 参数说明 2,596 字符 ≈ 649 token（JSON schema 结构还要再加）
→ 缓存前缀 ≈ 1,400–1,500 token
```

工具块在请求里排在消息**之前**。自动缓存按前缀精确匹配，所以**一旦工具集合变了，从工具块往后全部落空**——这一轮剩下的每一步都按全价计费，而不是缓存价。

- 省下的：`document_outline` 一个 schema，每步约 150 token；
- 付出的：约 1,400 token 的前缀在剩余每一步都拿不到缓存折扣。

只要一轮里还剩两步以上，这笔就是亏的。而调用过索引的，通常正是长运行。

→ 修法：撤掉这处 `activeTools` 切换，改用**结果里的一句话**（索引已在上文，不必重读）——那句话在消息区，不动缓存前缀。反直觉但可测：产品自己的用量面板就显示 `cachedInputTokens`，改前改后各跑一轮长问题即可验证。

### 1.3 提示里的一句假话 · V86

```
agent.ts:1032  .describe("Max hits to return (default 50)")
agent.ts:126   DEFAULT_SEARCH_HITS = 12
```

7.1 把默认命中数从 50 降到 12（省了约 2,600 token），但参数描述还写着 50。模型看的是描述：它想要「大约 20 条」时会觉得不传参数就够，实际只拿到 12，然后多搜一次。

→ 修法：一行。顺带核对其余 `.describe` 与真实默认值是否一致。

### 1.4 去重逻辑零测试 · V87

```
grep "delivered|already returned|ALREADY_READ" src/lib/*.test.ts → 0
```

7.2 最值钱的那条改动没有任何测试。V84 之所以能存在这么久，正是因为没有一条测试会去问「换成 `read_pdf_page` 还成立吗」。

→ 修法：补一组覆盖上表四种组合的测试。修 V84 之前先写，让它红。

## 2. 会话 · V88

### 2.1 ~~答案里的页码不能点~~ —— 撤回，这条是错的 · V88

**这条发现不成立，功能早已存在。** 我只 grep 了 `MessageContent.tsx` 就下了结论，而实现在别的文件里：

```
src/lib/remark-page-refs.ts   remark 插件，"page 5" / "pp. 12-14" / "第 5 页" → pagewise-page:<n>
src/components/Markdown.tsx   PageRefLink + PageRefContext
src/pages/ChatPanel.tsx:327   <PageRefContext.Provider value={onJumpToPage}>
src/lib/remark-page-refs.test.ts  9 条测试，全绿
```

而且做得比我打算提的方案更细：中英文都覆盖，`p.`/`pp.` 要求有点号（否则 "MVP 2024"、"top 10" 会被误链），`page` 要求词边界（否则 "webpage 5"），代码块和已有链接跳过，范围引用指向首页。

教训与这一轮 V84 是同一个：**只查一个文件就断言某个能力不存在**，和只在一个读取器里实现去重、然后声称整条保证成立，是同一种错误。断言「没有」比断言「有」需要更多证据。

→ 本条无事可做。会话轴的名额改由 §2.2 顶上（见下）。

### 2.2 仍缺的两件（7.2 已排到本轮）

- **对话不能用键盘走**——命令面板覆盖全局动作，对话内部没有「上一条回答 / 下一条引用」。
- **不能从某一轮分叉**——可以编辑重发（覆盖后续），不能「保留原来那条、另开一支」。

→ V88 撤回后，**键盘导航接替它成为本轮会话轴的内容**：它自成一体，只动 `ChatPanel` 的键盘处理，不改数据结构。分叉要改会话的存储形状（一棵树而不是一条链），继续排后。

## 4. UI · V90–V91

### 4.1 面收敛做了一半 · V90

```
仍自定义「背景 + 圆角」的 CSS 规则：33 条（7.2 前是 79）
<Panel> 调用点：9 处（7.2 前是 0）
CSS 总行数：5,324
```

7.2 把最像面的那几个转了，剩下 33 条里混着两类东西：真正该收敛的（几个菜单、卡片），和**本来就不是素面的**（带色调的提示条、虚线框、kbd 键帽）。后者不该硬转——上一版已经因此主动放过两个。

→ 修法：逐条过一遍这 33 条，明确分成「转」和「不转，因为它是 X」两堆，**把后者写进注释**。收敛的价值在于以后没人再需要重新判断一次。

### 4.2 两个组件大到无法阅读 · V91

```
AiProviderSettings.tsx   814 行
ChatPanel.tsx            695 行
PreviewPane.tsx          577 行
（全部组件合计 7,209 行 / 38 个文件，均值 190 行）
```

「界面粗糙」到这一步已经不是样式问题了。814 行的设置组件里塞着六个供应商的表单状态、连接测试、模型校验、迁移提示——每加一个供应商都要在这一个文件里再绕一圈。

→ 修法：只拆 `AiProviderSettings`，按「表单状态 / 连接测试 / 模型选择」三块抽出去。**不动 `ChatPanel`**——它是这一轮键盘导航要改的地方，同时拆分和改功能会让两件事都不可复查。
