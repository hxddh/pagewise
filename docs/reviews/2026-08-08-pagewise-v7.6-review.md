# 7.6 评估：token 这条已经挖到单点了，UI 这条一次结构性的都还没做过

日期：2026-08-08 ｜ 基线：7.5.6（已发布）
实测编号接续 `2026-08-06-pagewise-v7.5-review.md`（V1–V104）。

---

## 0. 结论

**7.5.1 到 7.5.6，六个补丁版本，每一轮都是一个 bug。** 这本身是信号。token 这条轴上还能挖出来的东西已经是单点缺陷——某个函数忘了除以 DPR、某个遗忘范围比重扫范围大——而不是结构问题。结构问题在 7.0 到 7.5 之间被逐层拆掉了：运行内重复、跨轮次重复、按页重复、附件重复、缓存前缀。这条轴该收工了，下一版不该再把它当主线。

**没有做过一次结构性整理的是 UI。** `App.css` 3,590 行，全文只有 **2 个分节注释**，75 个类名没有任何字面引用；而它理应构建其上的设计系统一共 387 行（tokens 105 + ui 282）。连续四轮评估写「UI 还是粗糙，必须质变」，四轮的回应都是往 3,590 行里再加规则。**「质变」在这里有确切含义：把 App.css 拆成有边界的部分，并且让 primitive 覆盖率变成可测的数字，而不是再抛光一遍。** 这是一个 major 版本真正有活可干的地方。

**会话这条要先认账一件事：mid-run steering 已经有了，我差点当成缺口报上来。** `ChatPanel.tsx:216` 起，运行中发送不再被拒绝，而是停掉当前 run 再起一个新的。真正还缺的是**不丢弃当前 run 的注入式引导**——这是一个更窄、也更诚实的命题。

## 1. UI · V105–V107

### 1.1 App.css 是唯一没被治理过的地方 · V105

```
App.css        3,590 行   分节注释 2 条   死类名 75
settings.css     869 行
preview.css      482 行
ui.css           282 行   ← primitive
tokens.css       105 行   ← token
```

设计系统是真的：6 级字号、3 档圆角、7 档间距、5 个 primitive，`check:css` 保证每个 token 引用都能解析。问题是它只管住了 387 行，剩下 4,941 行 CSS 在系统之外自由生长。

具体到可测的两个数字：

```
App.css 里硬编码颜色（#rgb / rgba）        30 处
App.css 里硬编码尺寸（font-size/radius/…）  95 处
<Button> 66 : 原生 <button> 38
<Input> 21 ｜ <Field> 16 ｜ <Panel> 14 ｜ <TextArea> 4
```

95 处硬编码尺寸意味着字号和间距的"6 级 / 7 档"是一个**局部**事实。38 个原生 `<button>` 里有一部分是合理的（6.3 那轮已经论证过：卡片形按钮、`<details>` 的 summary 等），但没有任何机制区分"论证过的例外"和"还没搬"。

→ 这一轮该做的：把 App.css 按已经存在的功能边界切开（会话、预览、侧栏、命令面板、overlay、标记），每个文件带一句说明它管什么；把 30 处颜色和 95 处尺寸中能替换的替换成 token，替换不了的在原地写明为什么；给 `find-dead-css.mjs` 的 75 个名字逐个定性——删掉、或者写明它是运行时拼装的。**这些都是可测的，做完前后的数字要一起写进 CHANGELOG。**

## 2. 会话 · V108

### 2.1 已经有的（先说清楚，避免重复造）

```
ChatPanel.tsx:216   运行中发送 = 停掉当前 run + 起新 run（不是拒绝）
MessageContent.tsx  RunPlanStrip：survey / locate / read / answer 四相
                    ToolStepsBlock：可折叠步骤 + 单步耗时 + 可点击页码
                    PagesReadTrail：读过的页，可点击
remark-page-refs    正文里的「第 5 页」「pp. 12–14」可点击
useConversationKeys Alt+↑↓ 在轮次间跳
ConversationSearchBar 会话内搜索
MessageAssistantFooter 用量弹窗，含 cachedInputTokens
```

这一层比我预期的完整。**上一轮我差点把 steering 当成缺口报上来**——和 7.2 把可点击页码报成缺失是同一个错误，先查再写。

### 2.2 真正缺的：注入式引导

现在的 steering 是 **stop + restart**。代价写在它自己的注释里，而那句注释说得比实情乐观：

> "Page text stays in the local cache, so the new run picks those pages up for free"

**免费的是 vision 扫描，不是 token。** 新 run 依然要把那些页的正文作为工具结果重新送进上下文，按全价计费。一次 20 步、读了 8 页的 run 被打断重来，读过的页要重新进上下文一遍。

真正的注入式引导是：不停 run，把用户那句话作为一条消息追加到 `prepareStep` 返回的 messages 末尾，下一步就能看到。可行性是确定的——`prepareStep` 已经在改写 messages（`compactRunMessages` 就在那里），追加在最后一条 tool result 之后是合法的消息序列。

→ 这是会话轴上唯一一个既有明确收益、又不需要改数据模型的改动。收益可测：同一个"读偏了→纠正"场景，改前改后各跑一次，比 `inputTokens`。

**（分叉已于 7.5 决定不做，不再复列。）**

## 3. token · V109

**这条轴该降级为副线。** 结构性的四层重复已经全部处理：

```
7.0/7.1  跨轮次重复、reasoning 回灌
7.2/7.3  按页重复（delivered 账本）
7.5.0    附件重复
7.5.5    历史窗口的缓存前缀
```

固定前缀现在是：

```
system prompt      2,131 字符 ≈ 533 token
六个工具的描述+参数说明  2,944 字符 ≈ 736 token
                        合计 ≈ 1,269 token，逐轮命中缓存
```

运行时上限：`RUN_CHAR_BUDGET` 200,000 字符、20 步、`KEEP_RECENT_CHARS` 16,000、`MAX_OUTPUT_TOKENS` 8,000。这几个数字之间是自洽的。

还剩下的三件，按可信度排：

1. **显式缓存断点（可测，先测再做）。** 五个 provider 全部走 `@ai-sdk/openai` + baseURL。OpenAI / DeepSeek 是自动前缀缓存，不需要做什么；但 OpenRouter 转发到 Anthropic 系模型时，不带 `cache_control` 断点就**完全不缓存**。`model-capabilities.ts` 里有 `anthropic/claude-3.5-sonnet`，说明这条路可达。**验证方法现成**：用量弹窗已经显示 `cachedInputTokens`，选一个 Anthropic 路由跑一段长对话，看那一行是不是 0。是 0 就值得做，不是 0 就不做。

2. **跨轮次页面复用——查过了，现状是对的。** `budget.delivered` 每轮 `prepareCall` 清空，第二轮再读同一页会重新送全文。算过账：留在历史里是 5,800 字符 × 之后每一轮，重读是 5,800 字符 × 真正需要它的轮数。重读更省，除非几乎每轮都要。**不改。**

3. **按需截取而不是整页。** 一个定点事实问题拿到 6,000 字符整页，绝大部分用不上。但这需要一个本地相关性步骤，而做错了会伤答案质量。**这一版只做测量，不做实现**：统计一轮问答里页面文本的实际引用率，拿到数字再决定。

## 4. SDK 与封装 · V110

```
在用：ToolLoopAgent / prepareCall / prepareStep / activeTools / toolOrder /
      repairToolCall / experimental_refineToolInput / stopWhen(stepCountIs+自定义) /
      smoothStream / experimental_throttle / streamObject / ChatTransport /
      convertToModelMessages / validateUIMessages
```

SDK 这一层用得比我预期的深。`experimental_refineToolInput`、自定义 `stopWhen`、`toolOrder` 都不是常见用法。**没有值得为了用而用的剩余 API**——`Output.object` 不适用（答案是散文不是结构），`resumeStream` 早已论证过不适用（本地应用无服务端流），`dynamicTool` 无场景。

真正的封装问题不在 SDK 侧，在设置侧：

```
settings.ts                775 行
AiProviderSettings.tsx     759 行
llm.ts                     487 行
                           合计 2,021 行，测试覆盖稀薄
```

五个 provider × 两类模型（agent / vision）× profile 切换 × keychain 回退 × 错误格式化，摊在三个文件里。这是 `agent-tools` 在 7.4/7.5 之前的形状。**但不建议这一版动它**——UI 那条已经是一个 major 版本的量，两条结构性改动叠在一起会重演 7.4 那次"拆分只是把堆挪了个地方"。记下来，下一轮。

## 5. 建议的 7.6 范围

| | 内容 | 可测的验收 |
|---|---|---|
| 主线 | App.css 按功能边界拆分；颜色/尺寸 token 化；75 个死类名逐个定性 | 单文件行数、硬编码 30/95 降到多少、死类名清零或写明 |
| 主线 | 本轮触碰的每个组件补一条交互契约测试 | `src/components` 测试数 6 → ? |
| 单点 | 注入式引导：不丢弃 run 的用户纠正 | 同场景 `inputTokens` 改前/改后 |
| 测量 | Anthropic 路由的 `cachedInputTokens` 是否为 0 | 是 0 才做显式断点，否则不做 |
| 测量 | 一轮问答中页面文本的实际引用率 | 拿到数字再决定要不要做按需截取 |

**不做**：分叉（7.5 已决）；`toolApproval` 改动（维持现状）；多文档；设置层重构（记下来，下一轮）；三个 major 依赖升级（TypeScript 5.8→7.0、Vite 7→8、@vitejs/plugin-react 4→6）各自单独一轮，不与产品改动混。
