# v22 评估：第一次打开就能用

*2026-10-15。基线 main `e50fb11`（`VERSION 21.0.0`）。另有修补分支 `hotfix-21.0.1`（PR #155）。*

*口径沿用 v21 评审：**实测**＝在这个容器里量出来的；**读代码**＝`file:line`；**上游**＝GitHub API 读到的；**未量**＝没量。*

## 0. 结论

1. **21.0 带出了一个丢数据的回归，已先修，不等 v22。** 在 macOS 上从 Finder 双击 PDF 冷启动时，授权列表会被覆盖成只剩这一个文件，前端随后把其它最近文件连同它们的对话一起删掉。修补在 PR #155（21.0.1），见 §1。
2. **v22 最大的问题不在核对链，而在第一次打开。** 实测：**界面是英文时，中文扫描件的引文定位率从 87.8% 降到 2.2%**，因为 OCR 语言只看界面语言。再加上：默认提供商 DeepSeek 没有视觉能力，看图功能在默认配置下不可用；不需要 key 的 Ollama 不在首次设置里。一个英文系统上的新用户打开一份中文扫描合同，得到的几乎全是「未确认」。
3. **产品信号仍然是零。** v21.0.0 发布后 issue 为 0；v20.0.0 六个安装包合计下载 1 次。真实模型基线（`eval/baselines/`）仍然不存在，因为这个环境没有模型 key。21 个大版本至今，核心承诺（模型给的引文真在页上）没有一个真实模型的分母。
4. **建议**：v22 的主题是「第一次打开就能用」，三件必做（§3.1），外加 21.0 审查剩下的写路径收口（§3.2）。发布形态上，这些改动不涉及存储格式，按 v21 独立评审提出的 SemVer 口径应发 **21.1.0** 而不是 22.0.0；如果维持「每轮一个大版本」的惯例，请在 CHANGELOG 顶部写明大版本号不代表不兼容。

## 2. 第一次打开会遇到什么

### 2.1 OCR 语言跟着界面语言走（实测）

`resolveOcrLanguages` 自 16.0 起只看界面语言（`src/lib/preferences.ts:67-76`）：界面是中文用 `chi_sim+eng`，否则只用 `eng`。`ocr-service.ts:38` 的默认值同理。

同一套 eval，把语言固定为 `eng`（临时副本，未提交；与 20.0 记录同口径，2026-10-15）：

| 页面类型 | 21.0 记录 | 只用 eng |
|---|---:|---:|
| 中文散文 | 79/90 = **87.8%** | **2.2%** |
| 表格单元格 | 68.7% | 30.2% |
| 生成语料（门） | **84.1%** | **61.9%**（门是 ≥80%，不过） |
| 英文散文 | 99.1% | 99.1% |
| 改坏引文误定位 | 0.05% | 0.1% |

也就是说，英文系统上的读者打开中文扫描件，本地 OCR 基本读不出字；引文全部显示为「未确认」，而且没有任何提示告诉他原因。

修法（不加设置项）：按页面内容选语言。先用 `eng` 识别；如果识别结果的置信度低、且 pdf.js 或文件名提示有 CJK 字符，就用 `chi_sim+eng` 再识别一遍。或者更简单：只要文档有中文元数据或者文本层里有 CJK，就用双模型。验收用的就是上面这张表：界面为英文时，中文散文 ≥85%，生成语料 ≥80%。

### 2.2 默认提供商没有视觉能力（读代码）

`DEFAULT_SETTINGS.provider = "deepseek"`，默认模型 `deepseek-v4-flash`（`types.ts:165`），能力表里 vision 为 false（`model-capabilities.ts:20`）。所以在默认配置下：`read_figure` 用不了；本地 OCR 识别不好的扫描页也没有云端视觉兜底。README 说视觉模型是「可选的兜底」，但对默认用户来说这个兜底根本不存在，界面上也没说。

修法：二选一。一是首次设置选 DeepSeek 时说明一句「看图和扫描兜底需要另配一个视觉模型」，并给出入口；二是看图工具在模型不支持视觉时，对模型和读者都直接说明，而不是静默失败。后者成本更低，应该先做。

### 2.3 不需要 key 的路线被藏起来了（读代码）

首次设置只列出 OpenAI、DeepSeek、OpenRouter（`SetupAssistant.tsx:36`）。Ollama 是支持的提供商（`types.ts:2`），但要进「高级」才能选到。对于「本地处理文档」这个卖点，「完全不用 key、完全离线」本来是最强的一条路，却最难找到。另外也没有示例文档，读者第一次只能拿自己的文件试。

### 2.4 大文件第一次打开（读代码）

300 页的扫描件：自动扫描读到 50 页就停（这是有意设的帽），阅读线显示「已读 50/300，剩 250 页按需」，但**这一行没有按钮**（`ReadingLine.tsx:39-50`）。「读取没有文字的页面」这个命令在命令面板里，读者不知道。重试按钮也只在 `vision_failed` 时出现（`PreviewPane.tsx:313-317`）。

### 2.5 安装（上游）

没有公证。macOS 要跑 `xattr`，Windows 要点「仍要运行」。AppImage 95 MB，是 `.deb`（17 MB）的 5.5 倍，原因**未量**，大概率是 AppImage 自带了 WebKitGTK。

## 3. v22 的范围

### 3.1 必做：第一次打开就能用

1. **OCR 语言按文档内容选**（§2.1）。验收：界面为英文时，中文散文 ≥85%、生成语料 ≥80%，用同一套 eval，并在 CI 的 eval job 里加这组门（只用 eng 的情况作为回归测试）。
2. **视觉能力说实话**（§2.2）。模型不支持视觉时，`read_figure` 返回一句明确说明（不调用模型），系统设置里的视觉行在默认提供商下写明「需要另配」。验收：组件测试和工具契约测试各一条。
3. **停住的阅读线给出下一步**（§2.4）。在「剩 m 页按需」后面加「全部读取」按钮，直接走已有的「读取没有文字的页面」流程，确认对话框里写明页数和费用。不加新设置。重试按钮扩到所有失败原因。

### 3.2 必做：21.0 复核剩下的写路径

4. **保存对话框只授权它返回的那个路径**，而不是整个文件夹（§1 #2）。`write_target` 只接受那一个文件名，写完一次就撤销。
5. **临时文件名不与读者的文件冲突**（§1 #7）：用随机后缀，以 `O_EXCL` 方式创建，不跟随符号链接。
6. **「记录已满」每次被拒都提示**（§1 #3），同一文件 30 秒内去重，避免反复弹。
7. **「已读过」标记计入 `maxChars`，范围读限制页数跨度**（§1 #5）。
8. **拖放授权移到后台线程**（§1 #8）。

### 3.3 应做：便宜、有数据支撑

9. **把 Ollama 放进首次设置**，作为「不需要 key」的那一项（§2.3）。
10. **红色引文可以送去复核**，复核记录的键加上页码和段落指纹（v21 独立评审 §2.6，21.0 只加了 toast）。
11. **OCR 缓存读失败时不要抹掉另一种语言的结果**（`ocr-store.ts:147-148`）。§3.1 第 1 项落地后，同一文档会同时有两种语言的缓存，这条会从「CPU 浪费」变成「重复付费」。
12. **在这个容器里能量的那批，先量再决定修不修**：空闲 CPU、1,000 行大纲的挂载时间、hurry 结束后的重绘次数、每页 `getPageGeometry` 调用次数、页码和页边卡片是否被裁切、BM25 重建耗时。每一项接进 `perf-probe` 或 `ui:inventory`；超出预算才修。

### 3.4 需要你提供的

- **真实模型基线**：给一个 key（例如 gpt-4o-mini 或 DeepSeek），跑 `eval:live` 录一份提交到 `eval/baselines/`。它也会顺带量出每步实际的 `outputTokens`，那是拆分 `MAX_OUTPUT_TOKENS` 的前提。
- **公证**：需要 Apple 开发者账号。
- **真机验证**：21.0 / 21.0.1 的对话框、拖放、Finder 冷启动、Windows 路径。

### 3.5 不做

沿用 v21 两稿的「不做」清单：多文档、金额、首屏包、双 OCR 引擎、提示词里「每句必须带标记」、自动复核等。新增两条：

- **不加 OCR 语言设置。** 按内容自动判断就够，加一个设置等于把问题推给读者。
- **在有基线之前，不写 v23 方向评估。**
