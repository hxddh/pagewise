## 0.5 最严重的一条：滚动会按页产生计费的视觉调用 · V49

复查时发现的，**比性能问题严重得多，而且是我在 6.0.0 引入的**。

`PreviewPane` 有一个效应：当前页没有文本就自动送去视觉索引。

```tsx
const indexPage = doc.kind === "pdf" ? page : 1;
useEffect(() => {
  if (pageHasIndexableText(...)) return;
  ...
  indexPageInBackground(doc.path, indexPage);
}, [doc.path, doc.kind, indexPage, pageTextLen]);
```

而 `indexPageInBackground` → `ensurePageIndexed(path, page)`，**没有任何配额参数**——`DEFAULT_AUTO_INDEX_PAGES`（自动扫描 50 页）和 `DEFAULT_AGENT_SCAN_PAGES`（每问 20 页）都管不到它。

**翻页时代这是安全的**：`page` 只在用户主动翻页时变，一次点击最多一次计费调用。

**滚动之后它不再安全**：`page` 随滚动持续变化，滚过一份 200 页的扫描件 = **最多 200 次计费的视觉调用**，无人值守、没有确认框。而命令面板里那条"扫描全部未扫描页"是**先弹确认、并告诉你页数**的——现在滚动就绕过了那道闸门。

`pageInflight` 会去重并发、`docCache` 会跳过已索引页，所以同一页不会重复计费；但**第一次滚过整份扫描件就把账单打满了**。

→ 修法：只索引读者**停下来**的那一页。页码变化后静默 400–600 毫秒再触发，滚动经过的页一律不碰。这也正是这条效应本来的意思——"你正在看的那页"，而滚过去不叫在看。

## 1. 复查 6.0 的滚动，三处问题 · V47

### 1.1 每一次滚动事件都会重渲染所有挂载的页面

`PageScroller` 在 `onScroll` 里 `setScrollTop(top)`——每帧一次 React 状态更新。这本来靠 `PageSlot` 的 `memo` 挡住，但：

```tsx
<PageSlot …>
  {(state) => renderOverlays?.(p, state)}   // ← 每次渲染都是新的闭包
</PageSlot>
```

`children` 每次都是新函数，**`memo` 永远不命中**。于是滚动时每秒 60 次、每次把所有挂载页（连同 `MarkLayer` / `LinkLayer` / `SearchHighlight` / `RegionSelectLayer`）整棵重新协调一遍。

那些覆盖层自己的 `useEffect` 依赖是稳的，不会重复请求几何——**代价是纯粹的 React 协调开销**，但发生在滚动这个最不该卡的动作上。`memo` 目前是装饰品。

修法：`scrollTop` 用 rAF 节流（一帧最多一次），并把每页的 overlay 渲染函数按页缓存，让 `memo` 真正生效。

### 1.2 `measurePageSizes` 在打开时遍历每一页

```ts
for (let i = 0; i < pageCount; i++) {
  const page = await doc.getPage(i + 1);   // 每页一次
```

一千页的文档就是一千次 `getPage`，而 pdf.js 会把 page 对象缓存住。**打开一份大文档时这是一条后台跑满的链**，且没有上限。

当时的设计取舍是"先出页 1，其余分批收敛"，这一半是对的；但没有任何东西阻止它一路跑到第 1000 页。修法：只测可见窗口附近的页，其余沿用首页尺寸，滚到哪测到哪。

### 1.3 ref 回调返回清理函数，`containerRef` 永远收不到 `null`

```tsx
const bind = useCallback((node) => {
  containerRef?.(node);
  …
  return () => ro.disconnect();     // React 19 的 ref cleanup
}, [containerRef]);
```

React 19 里 ref 回调一旦返回清理函数，卸载时就**只调清理函数、不再用 `null` 回调一次**。于是 `PreviewPane` 的 `scrollerRef` 和 `usePdfViewer` 的 `scrollerRef` 在预览卸载后仍指着一个已经离开文档树的节点。

实际后果轻微（组件同时卸载），但 `useAskSelection` 是拿这个 ref 判断选区是否在容器内的——**指着旧节点意味着这个判断在卸载后是错的**。修法：在返回的清理函数里显式 `containerRef?.(null)`。

### 1.4 还有一类我读不出来的

滚动的手感、快速滚动时的空白、缩放时视口位置是否守住、覆盖层在新容器里的实际落点——**这些只有跑起来才知道**。6.0.0 的回归正是这一类。所以 6.1 里这部分只能靠你反馈现象，我按现象修。

## 2. 签名：证书要你做，CI 那一半我可以先写好 · V48

现状确认：仓库里 `signingIdentity` / `APPLE_` / `codesign` 仍然零命中（`grep` 于本轮）。

**我能做的**：把 `release.yml` 的 macOS 那一路改成——

- secrets 里有证书 → 导入临时 keychain、设 `APPLE_SIGNING_IDENTITY`、正常构建（产物被签名）
- secrets 里没有 → **原样构建，不报错**

于是这件事对你就退化成：钥匙串访问里生成一张代码签名用途的自签名证书、导出 `.p12`、贴两个 secret。**不需要 Apple 开发者账号，不需要付费。**

为什么它能解决你遇到的两个提示：macOS 把钥匙串 ACL 和 TCC 都绑在 designated requirement 上；未签名/ad-hoc 的 DR 含 cdhash，每次构建都变；用固定证书签过之后 DR 变成 `identifier + certificate leaf`，**跨版本稳定**。

**这条推断我验证不了**（本环境没有 macOS）。但代价是你点几下，且失败也只是回到现状。
