# v24 评估：回答站得住，第一次用不出错

*2026-10-18，重写稿。基线 main `204e964`（`VERSION 23.0.0`）。口径同前：**实测**＝在这个容器里量出来或复现出来的；**读代码**＝`file:line`；**上游**＝GitHub API；**未量**＝没量。*

*第一稿只写了「先录基线，不做功能」，没有回答 v24 该把产品改成什么样。这一稿从三个方向重新看了 23.0.0：*

- *在真实运行的 app 里走一遍读者路径，在 1440×900 和 1024×700 两种窗口下截图；*
- *答案与引文的质量：跑 eval，并用实验补齐 eval 没覆盖的引文形态；*

*每一条都标了依据。*

## 0. 结论

1. **最大的问题在长回答的中途。** 一轮回答读的页多了，前面几页的原文会被压成一行摘要。这时重读，拿到的只是「已读过」的标记，而提示词又明确说「不要重读」。所以模型写答案时，前几页只能凭记忆引用，而引用要逐字核对，凭记忆的引文就会被判「未找到」。最需要读很多页的「列出 / 制表」任务，正好最容易撞上这一点（§2.1）。
2. **引文定位的 98.5% 只覆盖了「干净」的引文。** 用 eval 没覆盖的三种写法补测：
   - 带 Markdown 符号的引文：0/98；
   - 中间用「…」省略的引文：0/250；
   - 跨页的引文：0/5。

   前两种用很小的改动就能救回来：前者 0 → 88/98，误判率不变（§2.2）。
3. **读者路径上有两个看得见的缺陷：**
   - 回答下的「复制」「保留」两个按钮挤成了一个词「CopyKeep」，图标也丢了；
   - 「保留」切换标签页后会忘记自己已经按过，再按一次，记录和导出里就多出一条一模一样的结论（§3）。
4. **稳健性上最伤人的四条：**
   - 旋转过的页面，文字会静默丢掉；
   - 不知道模型的上下文窗口有多大，Ollama 默认约 4k，会静默截断；
   - 余额不足被报成「请稍后重试」；
   - 保存失败（比如磁盘满）完全不提示（§4）。
5. **建议**：v24（**24.0.0**）的主题是「回答站得住，第一次用不出错」。
   - 必做 12 项，每项都有可量的验收（§5.1）；
   - 真实模型基线照旧，用 GitHub Models 在 CI 里录，并按 §2.4 扩充题目；
   - 下载量仍然只有个位数（§1），这些修改先保证留下来的读者不被赶走。

## 2. 答案与引文

### 2.1 长回答丢掉前面的页（读代码，已核实）

- 同一轮里，只保留最近 16,000 字的工具输出，更早的压成一行摘要（`src/lib/compact-run-messages.ts:33`，`KEEP_RECENT_CHARS`）。
- 同一轮里再读同一页，返回的是 `ALREADY_READ_NOTE`，不是原文（`src/lib/agent-tools/reading.ts:401`、`:588`）。
- 系统提示词写着：「A page already returned in full this turn comes back as a short marker … do not re-read it」（`src/lib/agent.ts:169`）。

三者叠在一起：读到第 4、5 页以后，第 1 页的原文在上下文里已经没有了，也拿不回来。

- 审查者按 `gpl-3.0`（每页约 3.5k 字）推算，10 页里约 6 页会丢；这是推算，**没有真实模型的数**。
- 验收：一个确定性的回放测试，用真实的工具和压缩逻辑按顺序读完每份语料的每一页。到最后一步，每一页的原文要么还在上下文里，要么重读能拿回来。丢页数为 0。

### 2.2 eval 没覆盖的引文写法（实测，审查者的实验脚本）

| 写法 | 现在能定位 | 小改动后 | 误判 |
|---|---:|---:|---:|
| 原文逐字（现有 eval） | 1007/1022 | 不变 | 1/1997 |
| 带 `**`、`#` 的引文（模型读到的就是 Markdown） | 0/98 | 88/98（忽略字符里加上 `*#\` 和 U+2212） | 不变 |
| 中间用「…」省略 | 0/250 | 250/250（每一段都在页上） | 改动其中一段后被误判为找到：1/725。需要加距离上限 |
| 跨页 | 0/5 | 去掉页眉页脚之前只有 1/5 | — |
| 整行表格（单元格用空格连起来） | 55/61 | — | — |

提示词里的示例本身就是 `〔p12-13 "…"〕`（`agent.ts:166`），模型可能把它当成可以省略的许可。

### 2.3 已知的弱项（实测，`npm run eval`）

- 扫描件里的表格单元格：125/182（68.7%）；扫描件双栏：124/159（78.0%）。这两项都没有设门槛。
- 中文扫描件 87.8%，门槛 85%，余量最小。
- 搜索：36 个问题里，正确页出现在前三的有 32 个。漏掉的都是同义词或改写，比如问「保修期限」，合同原文写的是「质保期」。

### 2.4 基线该怎么录

`eval/live/run.mjs` 现在的局限：

- 只有单点查找题，没有列表或表格题、跨页综合题、文档里没有答案的题；
- 每题只跑一次；
- 工具调用只记了「有没有调用」；
- 不检查答案对不对。

建议第一份基线：

- 约 120 题：现有 36 题，加上列表或表格 25 题、跨页 15 题、无答案 15 题、扫描页 20 题；
- 每题跑 3 次；
- 打分项：引文能否定位、页码对不对、要求的事实或数字在不在、无答案题是否正确拒答、凭空编造的引文占多少。

审查者估算一轮约 1,000 万到 1,500 万输入 token，用 gpt-4o-mini 约 2 美元。

## 4. 稳健性（实测，构造的输入）

| # | 问题 | 依据 | 改法 |

| 1 | 带 `/Rotate 90` 的竖版页（在阅读器里旋转后另存就是这样）：给模型的页面文字每页丢 7 行（40 行里少 7 行），定位用的文字块却是全的。助手可能据此说「文档里没有」 | 实测 `rot90.pdf` | 按未旋转的 MediaBox 裁剪；加一份旋转的测试样例 |
