# 6.2 评估：滚动还留着两处翻页时代的坐标假设，以及那个一直没补的根因

日期：2026-08-04 ｜ 基线：6.1.0（已发布）
实测编号接续 `2026-08-04-pagewise-v6.1-review.md`（V1–V49）。

---

## 0. 结论

6.1 修的四条里，最重的一条（§0.5 计费）本质是**翻页时代的假设在滚动之后失效**：`page` 从"只在点击时变"变成"持续变"，一条没有配额的效应就失控了。

这一轮我按同一条线索又找了一遍——**还有哪些代码把"页面不动"当成前提**——找到两处（§1），都在区域选择上，都是确凿的坐标错位。另有一处小死键（§2）。

然后是那个我一直没补的根因（§4）：**这个应用有 50 个 `.tsx`、7906 行，从来没有一个在测试里被渲染过。** 6.0.0 的"无法翻页"、6.1 的三条，全都发生在这块盲区里，而且全是靠读代码发现的——两次我读完还是把回归发出去了。

---

## 1. 区域选择：两处坐标错位 · V50 / V51

`RegionSelectLayer` 在 pointerdown 记下 `e.clientX/clientY`（**视口坐标**），在 pointerup 时才读 `ref.current.getBoundingClientRect()` 当作 `pageBox`，两者一起交给 `clientRectToPageRect`。

### 1.1 拖框途中滚动，框就画错了 · V50

```tsx
onPointerDown: setBand({ x0: e.clientX, y0: e.clientY, ... })   // t0 的视口坐标
finish:        const box = ref.current?.getBoundingClientRect()  // t1 的页面位置
```

`setPointerCapture` 捕获的是指针事件，**不捕获滚轮**。拖框途中滚一下（或触控板两指、或键盘 Page Down），页面在视口里移动了，而 `y0` 还是滚动前那一帧的值——`y0` 和 `box.top` 属于两个不同的坐标系，算出来的 PDF 矩形整体偏移，偏移量正好等于这期间滚过的像素。

翻页时代不存在这个问题：那时页面在视口里是钉死的。

→ 修法：band 存**相对页面的坐标**（pointerdown 时就减去 `box.top/left`），而不是视口坐标。这样滚动多少都不影响。

### 1.2 拖出页面边界，矩形会落在页面外 · V51

指针捕获让整段拖拽的事件都留在起始那一页的层上，所以**框可以拖到页面外面**——拖到下一页、拖到列的空白区都行。而 `clientRectToPageRect` 全程只做线性换算，**没有任何一步把矩形夹回页面范围**：

```ts
const x1 = (selection.left - pageBox.left) * scale;   // 可以是负数
const y1 = (selection.top  - pageBox.top ) * scale;   // 可以超出页高
```

结果是一个部分（或完全）落在页面外的 PDF 矩形：`extract_region` 取不到文本，标记画出来也在页外——`.pdf-page-slot` 没有 `overflow: hidden`（V51），所以它会压在邻页上。

→ 修法：`clientRectToPageRect` 里把选区先夹进 `pageBox`，夹完宽或高为 0 就当作没画。这一条同时保护文本选区那条路径。

## 2. Home / End 在当前页内是死键 · V52

```ts
const goToPage = (next) => {
  const clamped = Math.min(totalRef.current, Math.max(1, next));
  if (clamped !== pageRef.current) onPageChange(clamped);   // ← 相同页号直接返回
};
```

- 在第 1 页中间往下滚了半页，按 **Home**：`clamped === 1 === page`，什么也不发生。
- 滚到最后一页顶部，按 **End**：同理，不动。

翻页时代"到第 1 页"和"在第 1 页顶部"是同一件事，滚动之后不是了。而且 **End 的语义也变了**：读者按 End 期望到文档末尾，现在即使生效也只是"最后一页的顶部"。

→ 修法：Home/End 不走 `goToPage`，直接把滚动容器送到 `0` / `scrollHeight`。

`MarkSidebar` 有筛选、有跳转、有笔记，**没有"就这条提问"**（整个文件里只有关闭和跳转两个按钮）。

## 4. 根因：50 个组件，0 个被渲染过 · V54

```
find src -name '*.tsx' | wc -l        → 50
cat $(find src -name '*.tsx') | wc -l → 7906
find src -name '*.test.tsx' | wc -l   → 0
vitest.config.ts                       → environment: "node"
devDependencies                        → 无 jsdom，无 @testing-library/*
```

49 个测试文件、424 条测试，**全部测的是纯函数**：`page-layout.ts` 被 20 条测试钉死，用它的 `PageScroller` 一条也没有。6.0.0 那次回归——`flex: 1` 在 row flex 容器里把高度塌成内容高度——**任何一次真正的渲染都会立刻暴露**，而它一路走完了 424 条测试、三平台构建和发布。

这不是"再多读一遍代码"能解决的问题，我已经证明了两次读不出来。

→ 修法：`jsdom` + `@testing-library/react`，`vitest.config.ts` 按目录切换环境（`.tsx` 用 jsdom，其余保持 node，不拖慢现有 424 条）。第一批只钉住这次滚动改造真正改掉的行为：

1. 滚动容器有高度、能滚（6.0.0 那条）
2. 滚到某处，报告的页号是覆盖视口最多的那一页
3. 滚过 N 页只索引停下来的那一页（6.1 §0.5，端到端而不只是 `settle` 单测）
4. 卸载后 `containerRef` 收到 `null`（6.1 §1.3）
5. `PageSlot` 的 `memo` 在滚动时确实命中（6.1 §1.1）
6. 拖框途中滚动，矩形不偏（§1.1 的回归）

**代价要说清楚**：两个 devDependency，测试时间会从 4.8 秒涨上去（jsdom 起环境不便宜），以及 jsdom **没有布局引擎**——`clientHeight`/`getBoundingClientRect` 都要显式桩住。所以第 1 条（flex 塌陷）在 jsdom 里其实**测不出来**，它是纯 CSS 布局问题。这一点我不粉饰：jsdom 能钉住的是逻辑与协作，不是真实布局。真实布局要么靠你在真机上看，要么将来上 Playwright（这个环境有预装 Chromium，但驱动整个 Tauri 应用是另一回事）。

即便如此，第 2–6 条都是 jsdom 覆盖得住的，而 6.1 的四条里有三条属于这一类。
