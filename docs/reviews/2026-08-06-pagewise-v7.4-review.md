# 7.4 评估：又一个建好没人用的原语，这次它本该修的无障碍问题还在

日期：2026-08-06 ｜ 基线：7.3.0（已发布）
实测编号接续 `2026-08-06-pagewise-v7.3-review.md`（V1–V91）。

---

## 0. 结论

**UI 这条最难堪：`Field` 原语真实调用数是 0。** 和 7.1 的 `Panel` 一模一样，而且这次更糟——`Field` 的注释里写着它是为了修「有的有 `htmlFor` 有的没有」而建的，**那个问题在 7 处手写字段里一个都没修**：3 处是 `<div>` 包 `<span>`，没有任何 label 关联，也就是**三个控件没有可访问名称**。其中一处是我 7.3 抽 `ApiKeyField` 时原样搬过去的。

同时 **40 个裸 `<button>` 对 50 个 `<Button>`**——44% 的按钮绕过了原语。

token 这条最值钱的是 **`document_outline` 每次返回 200 页的逐页字符数，约 1,273 token，而模型对这个数据无事可做**。顺带：那段注释里为 previews 估的「40,000 字符 ≈ 一万 token」是错的，实测 19,693 字符 ≈ 4,900 token。

还有一条要撤回：**`resumeStream` 对本产品不适用**，我在 7.2 和 7.3 两轮里都把它列为「未充分利用的能力」，没有先确认它是否适用于一个没有服务端的本地应用。

## 1. token · V92–V95

### 1.1 索引每次驮着 200 页的逐页字符数 · V92

```
MAX_OUTLINE_PAGE_STATS = 200
allStats = pages.map(p => ({ page, chars }))
实测：200 条 {page,chars} = 5,093 字符 ≈ 1,273 token
带 previews 时          = 19,693 字符 ≈ 4,923 token
```

`document_outline` 是宽问题的第一个调用，它返回的 `pages[]` 是每一页的字符数。**模型拿这个能做什么？** 规划分块所需的信号已经分别给了：`totalChars`、`needsChunking`、`suggestedChunkSize`；「哪些页读不了」由 `unindexedPages` 给；「哪些页有图/表/链接/标记」各有自己的字段。逐页字符数剩下的唯一用途是「这页短那页长」，而读取工具自己会用 `truncated` / `nextStart` / `nextOffset` 处理分块——模型不需要提前知道。

→ 修法：默认不返回 `pages[]`，改为几个真正能据以决策的聚合量（最长的若干页、明显偏短的若干页）。要全量时和 `previews` 一样做成显式开关。

**顺带一处不准确**：这段代码的注释写「previews 200 页大约 40,000 字符——一次工具调用一万 token」，实测是 19,693 字符 ≈ 4,900 token。夸大了一倍。数字被用来论证设计，就该是量出来的。

### 1.2 常驻说明只搬走了一条 · V93

7.2 把 `UNINDEXED_NOTE` 移进系统提示（265 → 34 字符），但同类的其余五条原地未动：

```
indexingFailedNote  150 字符 ≈ 37 token
figuresNote         119 字符 ≈ 29 token
linksNote           111 字符 ≈ 27 token   （读取结果里）
linksNote           105 字符 ≈ 26 token   （索引结果里，另一份措辞）
marksNote           104 字符 ≈ 26 token
```

这些**按次重发**：一次读 10 页、页上有链接和标记，`linksNote` + `marksNote` 就重复 10 遍，约 2,150 字符 ≈ 530 token 说同样两句话。而且 `linksNote` 有两份不同措辞，说明没人把它们当成同一件事。

→ 修法：与 7.2 同样的处理——常驻的话进系统提示（一次性、落在缓存前缀里），结果只留短标志位。**这次要把五条一次做完**，否则下一轮还会有人写「7.2 只做了六分之一」。

### 1.3 工具返回值没有共享形状 · V94

```
六个工具的返回字段种类：19 / 10 / 1 / 2 / 3 / 18
共享返回类型：无（grep interface.*Result → 0）
agent.ts 里 return { 出现 31 次，每处各自拼装
```

这不是洁癖问题：**V92 和 V93 之所以能长期存在，正是因为没有一个地方能一眼看全「工具到底往上下文里放了什么」。** 每个 `return {}` 各拼各的，19 种字段和 1 种字段的工具并排放着，没人会发现其中一个每次多塞 1,273 token。

→ 修法：给读取类工具一个共享的返回类型（文本 + 页码 + 截断信息 + 可选附件），附件（links / marks / figures）统一走一个字段。收敛之后 V92/V93 这类问题会变成类型层面看得见的东西。

### 1.4 复查过、结论是不用改

运行内压缩、跨轮次窗口、按页去重（7.3 已修全）、视觉扫描的 1568px/0.85、`MAX_OUTPUT_TOKENS`、`RUN_CHAR_BUDGET` —— 都复查过，合理。写在这里是因为你要求「每个环节」。

## 2. 会话 · V95

宽范围确认过现状（这次不只查一个文件）：

```
fork / branch                     → 0     不能分叉
searchMessages / filterMessages   → 0     会话内不能搜索
regenerate / editUserMessage      → 有
runPlan（计划视图）                → 有
Alt+↑/↓（7.3 新增）                → 有
saveChat(path, msgs)              → 一个文档一条会话
```

仍缺两件，按价值排序：

1. **会话内搜索。** 二十轮之后想找回「它当时怎么说第 40 页的」，只能用 Alt+↑ 一条条翻。Codex 和 Cursor 都能在会话里搜。纯前端、零 token，且和 7.3 的键盘导航是同一套焦点机制——搜到即跳。
2. **分叉。** 第三次排后了。它要把会话从一条链改成一棵树，是本轮所有事项里唯一动数据形状的，值得单独一轮，不该和别的混。

**一条「考虑过、不算缺口」**：`saveChat(path, msgs)` 意味着一个文档一条会话，没有会话列表。对一个 PDF 阅读 agent 这是对的——会话的身份就是文档的身份。不改。

## 3. SDK 与工具封装 · V96–V97

### 3.1 `resumeStream` 不适用 —— 撤回 · V96

我在 7.2 和 7.3 的评估里都写了「仍未使用的能力：`resumeStream`（崩溃后接回未完成的流）」。**这条不成立。**

```
useChat + 自定义 PagewiseChatTransport，代理在渲染进程内直接跑
没有服务端路由，没有 stream store
崩溃 = 进程没了，没有「还在跑的流」可以接回
重启后的悬挂工具调用已由 sanitizeDanglingToolParts 处理
```

`resumeStream` 是给「服务端在跑、客户端断线重连」用的。本产品是本地桌面应用，这个形状不存在。连着两轮把它列在待办里，是没有先问「它适用于这个架构吗」。

### 3.2 `agent.ts` 一个文件装了五件事 · V97

```
agent.ts 共 1,316 行
  六个工具定义         602–1,120   475 行
  系统提示                          ~30 行
  ReadBudget + 去重账本
  readPageRange / readPageText / withPageLinks / withPageMarks
  ToolLoopAgent 配置（prepareCall / prepareStep / repairToolCall / toolOrder）
```

它是全仓库最大的文件，而且是同时改 token 行为和工具行为时必须打开的那一个。7.3 的 V84（去重漏了一个读取器）就发生在这个文件内部——两个读取器隔着 200 行，没人会同时看到它们。

→ 修法：把六个工具移到 `src/lib/agent-tools/`（一个文件一个工具，共享的读取器和附件拼装抽成模块），`agent.ts` 只留代理配置与提示。这和 §1.3 的共享返回类型是同一件事的两面，一起做。

## 4. UI · V98–V99

### 4.1 `Field` 原语零调用，它要修的无障碍问题原样还在 · V98

```
<Field> 真实调用点：0（和 7.1 的 <Panel> 一样）
手写字段：7 处（settings-field / -label / -hint）
其中 label 元素：7 个全是 <span>，0 个带 htmlFor
包裹元素：4 个 <label>（隐式关联，可用）
          3 个 <div>（ApiKeyField、ModelSelect ×2）→ 控件没有可访问名称
```

`Field.tsx` 自己的注释写着：「标签、控件和下面的说明在每个调用点各拼一遍，**这就是为什么有的有 `htmlFor` 有的没有**」。原语建好了，注释写对了，**然后一个调用点都没改**，所以那三个控件到今天仍然没有可访问名称。

其中 `ApiKeyField` 那处是**我 7.3 抽组件时原样搬过去的**——搬运的时候没有顺手修，也没有发现。

→ 修法：7 处全部改用 `Field`。这不是收敛，是修一个真实的无障碍缺陷。

### 4.2 44% 的按钮绕过按钮原语 · V99

```
<Button>  50 处
<button>  40 处   ← 44%
<Input>   12 处 / <input> 4 处
```

`Button` 承载的是焦点环、禁用态、尺寸和图标按钮的一致性。40 个裸按钮各自决定这些，这正是 6.x 那几次「按钮看起来能点但没反应」「失败态没有样式」的来源。

→ 修法：逐个过一遍这 40 处，能转的转，**不能转的写明原因**（比如 `.provider-cell` 这类卡片形按钮，7.3 已定性为不该套 Panel，但它仍然应该是 `Button`）。和 7.3 的面分类一样，价值在于以后不用重新判断。

## 5. 建议

**7.4 = §1.1 + §1.2 + §1.3（token 三条）+ §2 会话内搜索 + §3.2 拆 agent.ts + §4.1 + §4.2。**

§4.1 优先级最高——它是一个真实缺陷，不是整洁度问题，而且修它的东西已经躺了两个版本。§1.3 和 §3.2 是同一件事，一起做才有意义。

§2 分叉单独一轮（唯一动数据形状的）。三个 major 依赖升级（TypeScript 7 / Vite 8 / plugin-react 6）各自单独一轮，仍不与产品改动混版。
