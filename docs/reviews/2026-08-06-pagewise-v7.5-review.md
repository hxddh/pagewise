# 7.5 评估：去重省下的页，附件又原样发了一遍；上一版的拆分只是把堆挪了个地方

日期：2026-08-06 ｜ 基线：7.4.0（已发布）
实测编号接续 `2026-08-06-pagewise-v7.4-review.md`（V1–V99）。

---

## 0. 结论

**7.3 花了一整轮做的按页去重，被附件绕过了。** 范围读取里，一页命中去重后只回一行标记——然后 `withPageLinks` / `withPageMarks` 仍然按 **整个范围** 计算，把那一页的链接和标记原样发出去。单页读取的早退分支不带附件，范围读取带——**同一个保证，两个读取器给的答案不一样**，和 7.3 修的那个 bug 是同一个形状。

**标记附件没有长度上限。** 索引里的标记摘要限 120 字符，逐页读取里一个都不限：单条最长 500（正文）+ 2,000（备注）。而标记的正文**就是被读那一页的原文**——它和页面文本在同一个返回值里出现两次。

UI 这条要认账：**`agent-tools/index.ts` 是 1,106 行。** 7.4 评估写的是「一个文件一个工具」，我把六个工具原样搬进了一个文件。`agent.ts` 确实从 1,347 降到 274，但那 1,106 行只是换了个位置。

同样：**`ChatPanel.tsx` 839 行，现在是全仓最大的组件。** 7.3 和 7.4 的评估各说过一次「这一版别拆它，因为正要在里面加功能」——然后两版都在里面加了功能。理由每次都成立，累计的结果不成立。

## 1. token · V100–V102

### 1.1 附件不看去重账本 · V100

```
readPageRange 结尾（agent-tools/index.ts:458-459）：
  ...withPageLinks(doc, rangeOf(from, lastPage), …)
  ...withPageMarks(path, rangeOf(from, lastPage), …)
                        ↑ 整个范围，不问哪几页真的发了正文
read_pdf_page 的早退分支（:747）：不带任何附件
```

`read_pdf_range(10,20)` 第二次调用时，10–20 页全部命中去重、正文只回 11 行标记——但这 11 页的**全部链接和标记照发**。去重省下的是页面文本，附件把省下的一部分又还回去了。

两个读取器对同一个问题给出不同答案，这正是 7.3 修的那个 bug 的形状：**保证写在一个地方，另一条路径不知道**。

→ 修法：附件只覆盖本次真正返回了正文的页。范围读取已经知道那是哪几页（去重分支里 `continue` 掉的就是），把它记下来传给两个 `withPage*` 即可。

### 1.2 标记附件没有上限 · V101

```
mark-store：MAX_MARK_TEXT = 500  MAX_NOTE_TEXT = 2,000  → 单条最多 2,500 字符
索引路径：  MAX_OUTLINE_MARK_CHARS = 120（有截断）
逐页读取：  withPageMarks —— 无任何截断
```

一页上 5 条标记就可能是 12,500 字符（≈3,100 token）挂在一次 6,000 字符的页面读取上，**比被读的页本身还大**。而且标记的 `text` 字段按定义是「做标记时那些字下面的词」——**它就是同一个返回值里页面正文的一段**。同一段文字在一个工具结果里出现两次。

索引路径已经想明白了这件事，注释写着「索引是用来定位标记的，整段正文由页面读取给出」。逐页读取没有对应的那句话，也没有对应的截断。

→ 修法：读取结果里的标记只留定位所需（页码、截断到 120 字符的正文、备注），和索引路径同一个上限。整段正文本来就在同一个结果的页面文本里。

### 1.3 复查过、结论是不用改

7.4 新做的 `densestPages`、五条常驻说明的搬迁、`ReadResult` 类型、运行内压缩、跨轮次窗口、缓存前缀完整性——都复查过，成立。`read_pdf_page` 的去重早退分支是对的（不带附件），问题只在范围读取那一侧。

## 2. 会话 · V102

**分叉第四次排后了。** 前三次的理由都成立：它要把会话从一条链改成一棵树，不该和别的混。但连续四轮「这一版不做」已经不是排期，是一个没有明说的决定。

现状（宽范围确认）：

```
fork / branch                 → 0
searchMessages（7.4 新增）     → 有
Alt+↑↓（7.3 新增）             → 有
regenerate / editUserMessage  → 有（编辑会覆盖后续）
saveChat(path, msgs)          → 一文档一会话
```

→ **已定：不做。**

理由是产品的，不是工程的：一个 PDF 阅读 agent 里，「保留原答案、另开一支」的需求远弱于编码 agent —— 读者要的是把一份文档读明白，不是并排比较两条推理路径。而代价是把会话从一条链改成一棵树，连带持久化迁移和一整套分支 UI。编辑重发覆盖了「上一问问偏了」这个真实场景，那是这里绝大多数分叉需求的实际形状。

**这条从此不再出现在评估里。** 连续四轮列一件不打算做的事，比不列更浪费注意力。

## 3. SDK 与封装 · V103

### 3.1 上一版的拆分只是把堆挪了地方 · V103

```
agent.ts             1,347 → 274 行  ✅
agent-tools/index.ts        1,106 行  ← 六个工具全在这一个文件里
  document_outline    542– 695  (153)
  read_pdf_page       695– 839  (144)
  read_pdf_range      839– 902  ( 63)
  read_section        902– 971  ( 69)
  read_figure         971–1039  ( 68)
  search_in_document 1039–1106  ( 67)
agent-tools/result.ts          82 行  ✅
```

7.4 评估原话是「把六个工具移到 `src/lib/agent-tools/`（**一个文件一个工具**，共享的读取器和附件拼装抽成模块）」。我做了目录和共享类型，没做一个文件一个工具。

这不是纯洁癖：V100 就是「范围读取和单页读取对同一件事处理不一致」，而这两个读取器现在仍然在同一个文件里隔着 200 行——**和 7.3 那次一模一样的距离**。

→ 修法：`reading.ts`（`readPageText` / `readPageRange` / 去重账本 / 附件拼装）+ 六个 `tools/*.ts`。附件拼装抽出来之后，V100 那种「一处改了另一处没改」在结构上就更难发生。

### 3.2 依赖又漂了

@ai-sdk/react   4.0.58 → 4.0.59   patch

## 5. 建议

**7.5 = §1.1 + §1.2（token 两条）+ §3.1 真正拆开工具 + §3.2 patch + §4.1 拆会话搜索。**
