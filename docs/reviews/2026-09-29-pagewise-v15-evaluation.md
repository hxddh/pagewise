# 15.0 评估：引文成立，不止引文存在

*2026-09-29。基线 14.1.0（已发布）。*

---

## 0. 结论

1. **13.0 到 14.1 回答的都是同一个问题："引文在不在原文里"。**
   - 13.0：回答里的每条引用都在本地核对。
   - 14.0：扫描页也能核对。
   - 14.1：核对过的证据可以写回 PDF、导出成表格带走。

   这条线已经闭合。还没有回答的是下一个问题："**这句话和它引的原文说的是不是同一件事**"。
2. **现在最危险的错误，恰好是界面上显示为"已核实"的那一种。**
   - 模型引了一句真实存在的原文，结论却写错了：把"三十六个月"写成"24 个月"，把"万分之三"写成"千分之三"，把乙方的义务说成甲方的。
   - 这时 13.0 的检查结果是紫色的"原文已找到"，读者看到的是一条被核实过的错误结论。
   - 这比红色的"没找到"更糟：红色会让人去看原文，紫色会让人停止怀疑。
3. **15.0 建议：引文成立。** 分两层：
   - **本地数值核对：** 免费、确定、每条引用都查。句子里的每个数字、百分比、期限、金额，必须出现在引文所在的原文段落里；中文数字、大写金额、"百分之几"和阿拉伯数字按同一个值比较。不一致就单独标出，并写明是哪个数。
   - **模型复核：** 按需、付费、读者主动触发。把"这句话 + 它引的原文段落"交给读者自己配置的模型，只回答支持、矛盾或不足以判断，并给出理由。主体、否定、条件这些数字以外的错误，本地规则判断不了，交给这一层。
4. **同时建议做"覆盖可见"：** 一条回答读了哪些页；还有哪些页含有问题里的关键词，却没有被读。它和"成立"一起回答"这个回答靠不靠得住"：一个问的是说得对不对，一个问的是有没有漏。
5. **可行性已实测（§3）：**
   - 数值核对：诚实的结论零误报；故意改错一个数的，查出 90.4%。
   - 覆盖提示：模型首页读错的 9 个问题里，找回了 6 个。
6. **开工的第 0 步仍然是真实模型基线（`eval:live`，需要 key）。** 没有它，我们不知道真实回答里数字转述、单位换算有多常见，也就不知道 15.0 的提示会有多"吵"。这一步卡在 key 上，不卡在代码上。

## 1. 14.1 之后剩下的缺口

| 缺口 | 现状（代码事实） | 对读者的后果 |
|---|---|---|
| 引文存在，结论不成立 | `citation-check.ts` 只查引文是否出现在所引页上，不看引用前面那句话说了什么 | 数字、主体、否定写错的结论也会被标成"已找到" |
| 漏读不可见 | 回答底部只显示"已读页"（`collectReadPages`），没有"可能相关但没读" | 列表类回答看起来完整，其实可能只读了一部分页 |
| 模型表现未测 | `eval:live` 工具已就绪，还没有数据 | 无法判断提示词改动和新提示在真实回答上的效果 |
| 真机未测 | macOS、Windows 上的 OCR 耗时，带证据 PDF 在 Acrobat 或预览里的显示 | 只能靠发布构建加手动检查 |

## 3. 可行性实测

脚本放在会话临时目录，没有入库；15.0 开工后会转成正式的 eval 套件。

### 3.1 数值核对

**方法**
- 从语料中取出每一句含数量的原文，作为"诚实的结论"；它所在的段落作为引文上下文。
- 规则：结论里的每个数量，归一化后都必须出现在上下文里。
- 归一化覆盖：
  - 阿拉伯数字（含千位分隔符）；
  - 中文小写和大写数字（三十六、肆佰叁拾陆万捌仟），限定紧跟"个月、日、年、小时、学时、元"等单位的情形；
  - "百分之 / 千分之 / 万分之"和 %、‰；
  - 句首的条款编号（9.3）视为标签，不算作数量。

**结果**

| 情形 | 数量 | 结果 |
|---|---:|---|
| 诚实的结论（原文照录） | 256 | **误报 0** |
| 诚实的结论，把中文数字改写成阿拉伯数字（七十二小时 → 72 小时，三十六个月 → 36 个月） | 50 | **误报 0** |
| 把一个数字改错（+7） | 208 | **查出 188，占 90.4%** |

**漏掉的 20 条：** 改后的数字恰好在同一段落别处也出现过。按规则，这种情况不能判为矛盾，这是有意的保守。

### 3.2 覆盖提示

**方法**
- 36 道评测题，假设模型只读了它自己的查询排第一的那一页。
- 覆盖提示：在没读的页里，按读者原问题的用词排序，取前 3 页。

**结果**
- 首页读错的题：9 道。
- 覆盖提示把正确页找回来的：**6 道**。
- 漏掉的 3 道都是同义词问题（问"保修"，原文写"质保"），或者问题里的词在原文中都不出现。这正是 C 候选要补的。

### 3.3 还不知道的

- 真实模型改写数字的频率。比如"三十六个月"写成"三年"——单位换算，规则会提示"数字不在原文里"。这类提示是否常见，只有 `eval:live` 能回答。
- 模型复核的准确率。也要用真实模型测。

## 4. 15.0 范围

### 4.1 目标句

> 读者看到一条带紫色引用的结论，数字写错了。PageWise 在这条引用上标出"句中的 24 个月不在引文所在段落里（原文：三十六个月）"。读者点"复核"，由他自己的模型判断这句话是否被原文支持。另外，回答底部列出"第 14、22 页也提到了违约金，本回答没有读"，点一下就能补读。

### 4.2 设计要点

| 层 | 做法 |
|---|---|
| **数值核对放在哪** | 在 `checkCitation` 之后运行，只对"已找到"的引用做，且只用本地信息。三样输入：引用前那句话（`sentenceBefore`，表格里是整行 `rowClaim`）；引文命中的 run 所在段落（按行距把相邻 run 连成段落）；以及同页的文字。 |
| **新状态** | `mismatch`：引文找到了，句中的某个数不在原文段落里。 |
| **新状态的显示** | 琥珀偏红，文字写明是哪个数、原文附近是什么数。 |
| **新状态的措辞** | 它说的是一个可以核对的事实（"这个数不在那段原文里"），不是"结论错了"。 |
| **反馈给模型** | 和 `unlocated` 一样，在下一轮告诉模型哪一句的数字对不上。 |
| **单位换算** | 年、月、日按 12 和 30 换算后一致的，不判为不一致。金额的"万元"和"元"同理。其余换算一律提示，并说明"可能是换算"。 |
| **模型复核** | 每条已找到的引用旁边有"复核"。调用读者配置的模型，要求结构化输出 `{verdict: supports / contradicts / insufficient, reason}`（AI SDK 7 的 `Output.object`）。结果存入 `citation-check` 的缓存，并计入用量统计。 |
| **模型复核不做什么** | 不自动跑，不在后台批量跑，不当作本地核对的结果。 |
| **覆盖可见** | 回答结束后，用问题原文的词在未读页上做排序（`rankPages`），取前 3，显示为"可能相关但未读"。点击后以"补读这些页再回答"发出一条跟进提问。 |
| **覆盖可见的范围** | 只在列表或表格类回答、以及回答读的页少于文档页数时显示，避免在"第 3 页讲了什么"这种问题上多嘴。 |
| **记录与导出** | 数值不一致的引用不进"只保留核对通过的句子"。简报和带证据的 PDF 都跳过它。CSV 的"核对"列增加"数字不符"。 |

### 4.3 验收（全部进入 `npm run eval`）

1. **数值核对，误报：** 语料中诚实结论（含中文和阿拉伯数字互换）的误报 ≤ 0.5%。§3.1 实测为 0。
2. **数值核对，检出：** 改错一个数的检出率 ≥ 85%。§3.1 实测为 90.4%。
3. **单位换算：** 构造"36 个月 ↔ 三年""4,368,000 元 ↔ 436.8 万元"等正例，全部不报。
4. **覆盖可见：** 在 36 道题上，首页读错时，正确页进入提示前 3 的比例 ≥ 60%（§3.2 实测 6/9）；另外报告每题平均的提示条数。
5. **模型复核：** 用脚本化模型跑端到端（调用格式、缓存、显示）。准确率要等 `eval:live`。

### 4.4 不做

- **多文档：** 按决定，短期内不做。
- **本地 NLI 模型：** 多语言模型动辄几百 MB，和"安装包小、离线"的取舍冲突。数值以外的核对交给读者自己的模型，按需触发。
- **自动全量模型复核：** 会让每个回答的成本翻倍，而且"复核结果"本身也可能出错，不能默默替读者下结论。

---

## 5. 风险

- **提示太吵。** 单位换算、四舍五入（"约 440 万"）都会触发数值提示。已有的缓解：换算表；措辞是"不在原文里"而不是"错误"；只对已找到的引用运行。真实频率要看 `eval:live`。
- **段落边界。** 相邻 run 连成段落靠行距，双栏和表格页可能把别栏的数字并进同一段，造成漏报（偏向不报，方向是安全的）。
- **模型复核也会错。** 所以它的结果单独显示为"模型复核：支持 / 矛盾"，不改变本地核对状态，也不进入"已核对"的判定。

## 6. 实施记录（15.0.0）

*§4 的范围全部实现。开工前的第 0 步（`eval:live` 真实模型基线）仍然因为没有 key 未做。数值核对和覆盖提示的门槛都在本地语料上实测，模型复核用脚本化模型验证。*

### 6.1 做了什么

| 部分 | 实现 |
|---|---|
| 数量归一化 | `src/lib/quantities.ts` |
| 段落 | `src/lib/passage.ts`：从引文命中的 run 出发，在同一栏内按行距向上下扩展。 |
| "结论"的唯一定义 | `claimBefore`：句子，或表格单元格。remark 插件从回答源文取出结论，写进 chip 的链接；统计、保留、CSV、反馈给模型都调用同一个函数。 |
| 新状态 `mismatch` | chip 是实心红边，标题写出是哪个数；计数里单列；"只保留核对通过的句子"排除它；CSV 显示"已找到，但数字不符"；下一轮告诉模型是哪个数；记录里的结论同样适用（可信度为"存疑"，页面上画虚线，带证据的 PDF 不导出）。 |
| 模型复核 | `src/lib/claim-review.ts`：`generateObject` 结构化输出，一条引用一次短调用，结果缓存，切换文档时清空。回答底部的按钮写明要调用几次；chip 上用 ✓ / ✗ / ? 显示结论，与本地核对并列，不替代它。 |
| 覆盖可见 | `src/lib/coverage.ts`：问题里、同时出现在已读页上的词，才算数；未读页至少带一半这些词才被提示；作为第一条跟进建议显示。只在问题要求"全部"或回答是表格时出现。 |

### 6.2 与计划不同之处

- **单位换算只做了时间和金额。**
  - 时间：年、月、周、日，按 12 个月一年、7 天一周换算。
  - 金额：元、万元、亿元。
  - "工作日"单独比较，不和自然日换算。
  - 其他单位（学时、份、次等）只比较数值本身。
- **覆盖提示的排序改了。** §3.2 的方案是直接用问题去搜。实测发现，中文问题里大部分是措辞（"列出……中所有的……条款"），会让"至少包含一半的词"这条规则把真正相关的页过滤掉。所以改为只看问题中、同时出现在已读页上的词，也就是这个回答实际讨论的内容。
- **模型复核是"整条回答一次按钮"，没有做每条引用单独一个按钮。** 这样花多少次调用一目了然，句中也不会堆满按钮。

### 6.3 实测

| 套件 | 结果 | 门槛 |
|---|---|---|
| 数值：诚实结论被误报 | 0 / 199 | ≤ 0.5% |
| 数值：改写后（中文数字转阿拉伯数字、月换算成年）被误报 | 0 / 32 | ≤ 0.5% |
| 数值：改错一个数被查出 | 157 / 167（94.0%） | ≥ 85% |
| 覆盖：首页读错后，正确页在提示里 | 6 / 9 | ≥ 60% |
| `audit:claims` | 9 / 9 | — |

### 6.4 仍未验证

- 真实模型改写数字的频率，也就是新提示在正确回答上出现得有多频繁；以及模型复核本身的准确率。这两项都需要用 key 跑 `eval:live`。
- 覆盖提示在同义词上的漏检（3 / 9）。要补上，需要语义检索（候选 C）。
