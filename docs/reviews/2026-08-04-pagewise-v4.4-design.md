# PageWise 4.4 评估：文档里的链接，模型一个也看不见

日期：2026-08-04 ｜ 基线：4.3.0（已发布）
实测编号接续 `2026-08-03-pdf-inspector-validation.md`（V1–V22）。

前提不变：不考虑历史兼容；陈旧依赖直接删；不为"用满能力"而堆架构。

---

## 0. 结论：一件事，但是一件真的事

4.3 收尾时我写过"pdf-inspector 的可用面基本吃完了"。本轮复查发现这句话说早了一点——**不是上游还有能力没用，而是我们自己已经解析出来的数据里，有一份从没走到模型面前**。

`links` 在 4.0 就解析好了，一直只有预览层的 `LinkLayer` 在读。agent 读一页时拿到的是 Markdown 正文，而**提取器不会把超链接的目标写进正文**。于是：

> 用户问"第 12 页那个链接指向哪里"、"文中引用的那个 GitHub 仓库地址是什么"、"把这篇文档里的外部链接列出来"——模型答不出来，而答案就在内存里。

这和 4.3 的 `pagesWithFigures` 是**同一个形状的缺口**：数据造好了，通往它的路没造。区别是这次的缺口从 4.0 就存在，四轮都没看见。

上游仍是 0.1.7（V26），本轮依旧没有白捡的新能力。

---

## 1. 链接目标在正文里丢失了多少 · V23

`rich.pdf` 第 1 页，模型实际读到的正文全文：

```
# Report

## See <u>the specification</u> and <u>PageWise</u>.

## Tail text.
```

页面上有两个超链接，指向 `https://example.com/spec` 和 `https://pagewise.app/`。正文里**一个字符都没有**——锚文本是散文（"the specification"），目标只存在于 PDF 的注解里。这是现代文档的常态。

`paper.pdf`（作者习惯把网址印在正文里，属于对我们最有利的情形）29 条链接：

| 正文里能看到的 | 条数 |
|---|---|
| 完整 URL（含 scheme） | 1 |
| 去掉 `https://` 后可见 | 12 |
| **只剩域名，路径丢失** | **15** |
| **完全不可见** | **1** |

即便是最有利的文档，**29 条里有 16 条（55%）的目标无法从正文复原**。典型的 `tex.stackexchange.com/users/484/charles-staats` 在正文里只是一个人名。

## 2. `DocLink.text` 是一个死字段 · V24

`Link.text` 取自上游 `TextItem.text`，而上游对 `ItemType::Link` **填的就是 URI 本身**——实测 `paper.pdf` 29/29、`rich.pdf` 2/2 的 `text` 与 `url` 逐字相同。

它不是锚文本，是 `url` 的一份复制。全仓检索：**没有任何地方读它**（`LinkLayer` 用的是 `url`，`title`/`aria-label` 也是 `url`）。一个跨 IPC 边界的字段，每次开文档都序列化一遍，零消费方。

4.2 已经为同样的理由删过两个字段。这次不是删，是**换**：把 `text` 换成有用的东西。

---

## 3. 锚文本能不能拿回来 · V25

链接有 `rect`，页面文本行也有 `rect`，两者出自同一次 `extract_text_with_positions`、同一坐标系。按面积重叠匹配：

```
rich.pdf   2/2 恢复    "the specification" (82%)  "PageWise" (82%)
paper.pdf  29/29 恢复
```

**但恢复出来的不是锚文本，是整行。** 上游的文本粒度是行/文本 run，不是字符（模块文档里已经写明）。实测 `paper.pdf` 第 2 页：

```
锚文本（真实）  martin-thoma.com/geotopo
恢复出来的      "Das Skript ist kostenlos übermartin-thoma.com/geotopoverfügbar. Wer es gerne in A5 (Schwarz-"
```

### 由此否掉一个方案：不把 `[锚文本](url)` 写回正文

看上去最漂亮的做法是把正文改写成真正的 Markdown 链接——搜索不受影响（`markdownToPlainText` 会把 `[label](url)` 归一成 label）、导出还能带上链接。**但行粒度让它做不成**：会把整段话包进一个链接里，正文被改坏，收益变成损失。

按 4.3 对 `include_images` 的同一条标准：**信息属于元数据就放元数据**，不塞进正文。这次连"塞得进去"都不成立。

行本身仍然有用——它就是这条链接所在的**上下文**，比 URL 本身更能说明"这是谁的链接"。所以恢复出来的行留着当 `context`，只是不写进正文。

## 4. 方案

### 4.1 `Link.text` → `Link.context`

在 `collect_positions` 里一并算出来。那次遍历**现在就已经收到了全部 Text item，只是直接丢掉了**——把它们按页留住，与 Link 的 rect 求重叠，取重叠最大的一行。

零新增解析、零新增命令、零新增依赖。一次 `extract_text_with_positions` 换回两样东西而不是一样。

### 4.2 页读带上本页链接

`read_pdf_page` / `read_pdf_range` / `read_section` 的结果增加：

```jsonc
"links": [{ "url": "https://example.com/spec", "context": "See the specification and PageWise." }]
```

与正文分开，不进 ⌘F、不进导出、不改变搜索。与 4.3 选 `pagesWithFigures` 而不是 `include_images` 是同一个取舍。

### 4.3 `document_outline` 增加 `pagesWithLinks`

与 `pagesWithTables` / `pagesWithFigures` 完全对称。让模型在通读结构时就知道哪几页有外链可查。

### 4.4 预览层顺带受益

`LinkLayer` 的 `title` / `aria-label` 目前是裸 URL。有了 `context` 可以读作"链接：<上下文> → <域名>"，对读屏用户尤其明显。

## 5. 本轮考虑过、不做的

| | 否掉的理由 |
|---|---|
| 正文改写成 Markdown 链接 | §3，行粒度会把整段包进链接 |
| 文档内跳转（ToC → 页码） | 上游 `ItemType::Link(url)` 只给 URI，GoTo 目标够不着；且我们本来就合成大纲 |
| 扫描件快捷路径补上 links | 高置信扫描件没有文本层，注解链接实测为 0，补了也是空 |
| 样式边界丢空格（`übermartin-thoma.com`） | 上游提取缺陷，实测存在；在适配层修需要猜词边界，德语复合词上必错，不碰 |

---

## 6. 架构影响

命令数 **不变**（3 个）。一个字段换一个字段，一个已有工具的输出字段 ×2，一个纯函数（矩形重叠）。依赖**不新增**。

## 7. 版本号

建议 **4.4.0**：模型能回答一类它此前完全答不了的问题，属于新增能力；`Link.text` 换 `Link.context` 是内部结构变化，前端同步改，不涉及历史兼容。

## 8. 本轮实测

### V23：链接目标在正文里丢失

```
rich.pdf   正文 = "See <u>the specification</u> and <u>PageWise</u>."
           2 条链接的 URL 在正文中出现次数：0
paper.pdf  29 条链接 — 完整 URL 1 / 去 scheme 后可见 12 / 仅域名 15 / 完全不可见 1
           → 16 条（55%）目标无法从正文复原
```

### V24：`DocLink.text` == `url`，且无人读取

```
paper.pdf  text == url 的链接：29 / 29
rich.pdf   text == url 的链接：2 / 2
全仓检索 link.text 的读取点：0
```

### V25：按 rect 重叠恢复上下文可行，但粒度是行

```
rich.pdf   2/2   "the specification" (重叠 82%)
paper.pdf  29/29 但 p2 恢复出 90 字符整行，真实锚文本 24 字符
```

### V26：上游未发新版

`cargo search pdf-inspector` → 仍为 0.1.7，与 4.0 集成时相同。
