# 5.3 评估：pdf-inspector 收尾之后，剩下的最大一件仍是多文档

日期：2026-08-04 ｜ 基线：5.2.0（已发布）
实测编号接续 `2026-08-04-pdf-inspector-dig-round-8.md`（V1–V40）。

---

## 0. 结论

第八轮挖掘之后，`pdf-inspector` 这条线正式收尾了。分发在 5.2 打通了三个平台。**剩下的清单里，只有一件是"大的"：多文档。**

它在 5.0 时评估过、被你推迟，此后过了三个版本（5.0 / 5.1 / 5.2）。本轮复查它的前提有没有变——**变了，而且是往好的方向**（§2）。

另外本轮查了一件因为 Linux 刚上线而变得现实的事：**没有 keyring daemon 的机器上密钥怎么办**。结论是**已经处理好了，不需要做**（§1）——这条写出来是因为"查了没问题"和"没查"是两回事。

---

## 1. Linux 上线后的密钥落盘：查了，是好的 · V41

5.2 让 Linux 第一次有了安装包。Linux 的 `keyring` 走 secret-service，需要系统里跑着 keyring daemon——最小化桌面、WSL、很多开发机上都没有。那台机器上存 API key 会失败。

顺着查了一遍，**降级路径是完整的**：

```
persistApiKey()  → 失败返回 false（不抛）
writeStoreV2({ keychainOk: false })  → 把 key 镜像进 settings.json
hasPlaintextKeysOnDisk()  → 读回这个状态
AiProviderSettings.tsx:599  → 渲染 settings.plaintextKeysWarning
```

文案也没有粉饰：*"Secure storage is unavailable — API keys are saved on disk in plaintext. Avoid shared machines until Keychain access is restored."*

**应用不会因此不可用，用户也不会被蒙在鼓里。这条不需要做任何事。**

## 2. 多文档的前提复查：比 5.0 时更好了 · V42

5.0 那份评估（`2026-08-04-pagewise-v5.0-design.md`）的实测仍然有效，包括 §2.1 那处更正——`pdf.ts` 的单活动文档不变量是硬失败，不是降级。

**三个版本之后有两处变化，都是有利的：**

| | |
|---|---|
| **标记天生就是多文档的** | `mark-store` 的 `marksByPath` 是 `Map<path, Mark[]>`，`loadMarks(path)` / `forgetMarks(path)` 按路径进出。5.0/5.1 做标记时没有为多文档做任何准备，但它自然就是这个形状 |
| **仍然只有两处硬拦路** | `doc-cache.ts` 的 `MAX_CACHED_DOCS = 1`（一个常量），以及 `pdf.ts` 的 `pdfActivePath` / `shouldCommitPdfLoad`（真机制，见 5.0 评估 §2.1–2.2） |

也就是说：从 4.4 到 5.2 这四个版本，**没有一处新代码让多文档变得更难**——而标记这一层还自带了正确的形状。

5.0 定下的那条界线现在更成立了：**pdf.js 只服务预览，agent 对非预览文档的一切读取都走 Rust**。因为 5.1 之后，agent 唯一需要 pdf.js 的仍然只有 `read_figure`（区域标记用的是同一条路，但那是用户在预览里的动作，本来就是活动文档）。

## 4. 建议

**5.3 做多文档。** 理由：

1. `pdf-inspector` 收尾、分发打通之后，它是清单上唯一"改变产品是什么"的一件；
2. 前提复查下来只更有利，且 5.0 那份评估已经把地基和陷阱都测清楚了，不需要重新调研；
3. 其余候选要么是小事（可以搭在任何一版里），要么卡在你手上。

如果你仍想再推迟它，那么次优是**"就着标记提问"**——小、完整、修的是 5.0/5.1 自己留的单向连接。但它做完之后，清单上就真的只剩卡在你手上的两件了。
