## 0. 结论：该动的不是提取，是"一份"

4.0–4.4 五个版本全部在提取层里做文章，到 4.4 已经把 `pdf-inspector` 榨到有否定证据为止。继续往那个方向找，只能找到越来越小的东西。

真正限制这个产品的是另一件事：**PageWise 一次只回答关于一份文档的问题。**

而真实的工作从来不是一份文档：合同和它的补充协议、论文和它引用的那几篇、一个季度的三份报表、一个项目的标书与评标办法。今天要跨文档，用户只能：关掉 A、打开 B、重新解析、重新索引、并且丢掉刚才那条对话的上下文。

本轮最重要的发现是：**这件事的技术地基已经铺好了，锁死它的是上层的五处、其中一处只是一个常量。**

## 1. 栈的下半部分早就是多文档的 · V27

不是设想，是实测：

| 层 | 现状 | 证据 |
|---|---|---|
| Rust 路径白名单 | **集合** | `AllowedPaths` 是 `HashSet`，`register_allowed_path` 每次 `insert` |
| 白名单持久化 | **64 条** | `allowed-paths.ts` `MAX_PERSISTED = 64` |
| 视觉索引落盘 | **24 份 / 600 万字符** | `index-store.ts` `MAX_CACHED_INDEX_DOCS = 24`、`MAX_INDEX_CHARS = 6_000_000`，按 path + stamp 存取，已有淘汰策略 |
| 文档缓存 | `Map<path, LoadedDocument>` | `doc-cache.ts`——**是个 Map，只是上限写死为 1** |
| 索引队列 | **按文档分片** | `index-queue.ts` 的 `queues` / `pathGenerations` / `pageInflight` / `pageIndexFailure` 全是 `Map<path, …>` |
| 工具寻址 | 每个工具都走 `resolvePathInput(path, 默认活动文档)` | 三个工具的 schema 里已经有 `path` 参数 |

但**前端的 pdf.js 层不在其列**——它刻意维持单一活动文档，见 §2.1。

也就是说：**磁盘上已经同时存着 24 份文档的索引，Rust 侧同时授权着最多 64 条路径，而内存里只允许放 1 份。**

`MAX_CACHED_DOCS = 1` 不是架构，是一行策略。

## 2. 真正锁死单文档的五处 · V28

逐一核过，只有这五处：

1. **`doc-cache.ts`：`MAX_CACHED_DOCS = 1`** —— 一个常量。
2. **`SessionProvider`：`document: LoadedDocument | null`** —— 单数。所有 UI 从这里取。
3. **`chatId = document?.path`** —— 聊天线程绑在这一份上。这是唯一需要真正想清楚的一处，见 §3。
4. **三个工具还不收 `path`** —— `read_section` / `read_figure` / `search_in_document` 的 schema 里没有 `path`，执行时写死 `resolvePathInput(undefined, options)`。另外三个（`document_outline` / `read_pdf_page` / `read_pdf_range`）已经收了。**六个工具里三个是多文档的，三个不是。**
5. **`remark-page-refs.ts`：`pagewise-page:<n>`** —— 引用里的"第 5 页"只带页码，不带文档。多文档下这个链接是有歧义的。

6. **`pdf.ts`：pdf.js 侧的"单一活动文档"不变量** —— 见 §2.1。

前五处是常量和形状改动。第六处不是，它是本轮复查里最重要的更正。

### 2.1 更正：`pdf.ts` 里还有第六处，而且它不是常量 · V31

初稿写的是"没有第六处"。**这是错的。** 复查前端时发现 `pdf.ts` 有一整套刻意维护单一活动文档的机制：

```
pdfDocCache        = { path, doc } | null      —— 只存一个 PDFDocumentProxy
pdfActivePath                                  —— UI 正在看的那份
pdfDocEpoch / fileReadGen                      —— 换文档时递增，作废在途加载
StalePdfLoadError                              —— 非活动文档的加载结果被丢弃
shouldCommitPdfLoad(path, epoch)
   = epoch === pdfDocEpoch && (pdfActivePath === null || pdfActivePath === path)
```

后果不是"慢"，是**直接失败**：`pdfActivePath` 指向 A 时调用 `getPdfDocument(B)`，`shouldCommitPdfLoad` 恒为 false，四次重试外加最后一次直连全部抛 `StalePdfLoadError`——每一次都完整解析一遍 B、再销毁掉。既慢又拿不到结果。

另外 `SessionProvider` 打开新文档时还显式做了三件拆除动作：`cancelIndex(prevPath)`、`docCache.remove(prevPath)`、`clearPdfCache()`（销毁 proxy、清空字节缓存、位图缓存、文本层缓存）。

这套东西不是疏忽，是**为了解决换文档时的跨文档串渲染而专门建的**。不能当成常量随手放宽。

### 2.2 由此定下的一条界线：pdf.js 只服务预览，agent 走 Rust

清点了一下 agent 的读取路径实际依赖谁：

| agent 能力 | 依赖 |
|---|---|
| 页文本 / 大纲 / 链接 / 搜索 | `docCache`（Rust 解析结果），**不碰 pdf.js** |
| `read_figure` | `renderRegionToJpegBytes` → pdf.js 栅格化 |

也就是说**六个工具里只有 `read_figure` 需要 pdf.js**。Rust 侧的三个命令（`open_document_cmd` / `extract_region_cmd` / `page_text_items_cmd`）本来就是无状态按路径调用的。

所以界线是：**pdf.js 维持"单一活动文档"不变，只服务预览；agent 对非预览文档的一切读取都走 Rust。** 唯一的例外 `read_figure` 允许临时借用一次 pdf.js（借完预览重新加载自己那份，`paper.pdf` 量级约 0.8 秒），而它本来就要花一次计费的视觉调用、超时 60 秒——多这一秒可以忽略。

不做的替代方案：在 Rust 侧新增页面栅格化命令。`pdf-inspector` 不带光栅化器，要另加一个渲染依赖，与原则二正面冲突。

## 3. 聊天线程归谁：这一版唯一需要设计的问题

其余四处都是机械改动，只有这个是设计。列过三种：

| 方案 | 问题 |
|---|---|
| 线程属于"文档集" | 集合会随开关文档变化，线程 id 不稳定，持久化和淘汰都要重做 |
| 线程跟随当前预览的文档 | 我在 A 的对话里问了跨 A、B 的问题，切到 B 看一眼图，对话就换了——最难用的一种 |
| **线程属于你提问时所在的那份文档，其余文档可读** | 与今天的行为完全一致，只是把"可读"从一份放宽到一组 |

选第三种。具体地：

- **聊天文档**（`chatPath`）：线程的归属，就是今天的 `chatId`，**持久化格式一个字节都不用改**。
- **预览文档**（`previewPath`）：你正在看哪一份。可以与聊天文档不同。
- **打开的文档**（`documents`）：模型可读的全集。

切换预览不动聊天。要以另一份为主，就显式"在这份上开始新对话"——线程切换成为一个动作，而不是一个副作用。

两个指针，都是字符串。这是我能找到的最简单的、且不会在使用中咬人的模型。

## 4. 造好通往能力的路（4.3 和 4.4 的教训）

4.3 补的是"`read_figure` 造出来了但模型不知道哪页有图"，4.4 补的是"链接解析出来了但模型看不见"。**两轮都是同一个错误：造了能力，没造通往它的路。**

多文档会以最大的规模重犯这个错误——如果模型不知道还开着别的文档，`path` 参数就是死的。所以这一版必须同时：

- **新增 `list_documents`**：返回每份打开文档的 path、名称、页数、是否已索引。这是模型唯一能知道"还有别的可读"的途径。
- **补齐三个工具的 `path`**（§2.4），让六个工具口径一致。
- **读取结果里带上文档标识**：当读的不是聊天文档时，结果里必须有 `document`，否则模型会把 B 的第 5 页说成"第 5 页"。
- **`pagewise-page:` 带上文档**（§2.5），点击引用跳到**那份**文档的那一页。
- **系统提示改口**：今天写的是 "The user has one active PDF; omit path on tools to use it."——这句话在多文档下是错的，会主动阻止模型去看别的文档。

## 5. 代价实测：内存不是问题，重解析才是 · V29

放宽缓存上限的唯一技术顾虑是内存。实测（`paper.pdf`，117 页的书）：

```
整个 DocumentModel 序列化后   175 KB   （其中文本 153 KB）
release 解析耗时              816 ms
debug  解析耗时             9,515 ms
```

- **内存**：8 份这种量级的文档约 1.4 MB。相对于 PDF.js 的渲染缓存可以忽略。**这个顾虑不成立。**
- **重解析**：今天每次切回上一份文档都要重付 816 ms。这恰恰是保留缓存的理由，而不是反对它的理由。

上限定为 **8 份**，并按字符总量兜底（沿用 `index-store` 已有的那套写法），而不是靠份数硬扛——一份 2000 页的扫描件不该和八份小文档等价。

### 视觉索引的花费不会因此失控

自动全文索引只对**预览中的那份**跑，其余文档的扫描页在 agent 用到时才按需索引，而这已经被 `budget.maxScans` 每轮限死。多文档不会让账单翻倍。

## 6. 本轮顺带清掉的陈旧物

`model-capabilities.ts` 里的 `isEmbeddingCapableProvider` 与 `EMBEDDING_CAPABLE_PROVIDERS`：**全仓零调用点**，是某次语义检索方案撤掉后剩下的。按原则三直接删。

（同时这也是一条否定证据：语义检索在这个产品里试过并撤掉了。5.0 不重启它——跨文档检索先用现有的关键词搜索按文档逐份跑，简单、可预期、不依赖 provider 是否有 embeddings 端点。）

## 7. 本轮考虑过、不做的

| | 否掉的理由 |
|---|---|
| 一次调用搜遍所有打开的文档 | 收益是"少几次工具调用"，代价是搜索结果要带文档维度、截断规则要重设计。先让 `search_in_document` 收 `path`，模型逐份搜——简单、可预期。真成为瓶颈再说 |
| 文档集/工作区概念（可命名、可保存） | 这是"复杂架构"本身。打开的文档就是打开的文档，关掉就没了，和编辑器的标签页一样 |
| 跨文档的语义检索 / 向量库 | §6：撤过一次，且引入 provider 能力依赖与一整套索引生命周期 |
| 内置 OCR 取代视觉索引 | 需要引入 tesseract 量级的依赖，与原则二正面冲突 |
| 文档比对（diff 两份合同） | 真需求，但它是建立在多文档之上的**下一步**。这一版先把地基放开 |

## 8. 版本号

建议 **5.0.0**。不是因为改动量大——改动量其实不大——而是因为"一次一份"是 PageWise 从第一版起的核心前提，取消它改变了这个产品是什么。`SessionProvider` 的对外形状会变（`document` → `documents` + 两个指针），工具结果会多出文档维度。

## 10. 落地顺序

1. `doc-cache` 放宽上限 + 字符兜底（§5）——其余全部依赖它
2. `SessionProvider`：`documents` + `previewPath` + `chatPath`（§3）；打开新文档不再拆除旧的（§2.1 那三处显式拆除要按新语义重写）
3. 三个工具补 `path`、新增 `list_documents`、读取结果带 `document`（§4）
4. `pagewise-page:` 带文档，引用可跨文档跳转（§4）
5. `read_figure` 临时借用 pdf.js，用完归还预览（§2.2）
6. 预览层的文档切换 UI
7. 删掉 `isEmbeddingCapableProvider`（§6）

1–4 是能力，5 是那条界线的唯一例外，6 是可用性，7 是清理。1 与 2 之间有依赖，2 与 5 都触及 `pdf.ts` 的活动文档语义，应连着做；其余互不阻塞。

**工作量修正**：初稿按"五处、其中一处是常量"估的。加上 §2.1 之后，`pdf.ts` 与 `SessionProvider` 的文档切换语义是这一版真正需要小心的地方——不是因为难，是因为那套 epoch/stale 机制原本就是为了修跨文档串渲染而建的，改动它必须保住它当初解决的问题。
