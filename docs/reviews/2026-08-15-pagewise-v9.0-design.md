# PageWise 9.0 — the document remembers

*2026-08-15. Written after the 8.1.x visual sweep closed.*

## 1. What 8.1.x settled, and what it did not

Eleven releases between 8.0 and 8.1.8 were spent on one thing: making the app
visible. The Tauri IPC mock (`scripts/ui-harness/tauri-mock.mjs`) turned "the UI
is coarse" from an opinion into a list, and the list got worked through — nine
defects, every one invisible to the DOM tests that already existed, every fix
held by an invariant that was checked to fail on revert.

That work is done and it should not continue. It was *repair*, and repair has
converged: the last full sweep across ten surfaces and three window widths
turned up two defects, both of which were old bugs rather than new ones.

But the standing complaint was not "there are layout bugs". It was **UI 还是粗糙，
必须质变** — and nine fixed defects have not changed what the app *is*. Neither
have the token measures, which are real (intra-run compaction, inter-turn
summaries, a pinned prompt-cache prefix) and are all optimisations of the same
unchanged shape.

So this document does not propose a twelfth increment. It names one ceiling that
bounds all four standing axes at once, and proposes removing it.

## 2. The ceiling: PageWise forgets everything between questions

Read the tool surface as a reader would. There are six tools and they are all
**retrieval**: outline, literal search, read page, read range, read section,
read figure. There is nothing that *writes*. The agent can look at the document
and it can talk, and that is the whole of its relationship with the work.

The consequence is that every question starts from zero:

- The reader asks about the method on page 12. The agent reads page 12, answers,
  and the run ends.
- Six questions later the same page is relevant again. The agent reads page 12
  again — from scratch, at full token cost, deriving the same understanding it
  already had.
- `compact-run-messages.ts` makes that forgetting *cheap*. It does not make it
  *rare*. Its own comment is exact about this: a finished turn keeps
  `[Read page 12, 5,800 chars]` instead of the page.

Meanwhile the reader is accumulating understanding too — and it lands in a chat
transcript, which is linear, undifferentiated, and detached from the pages it is
about. Close the app and what survives is a log of questions, not a read
document.

**Marks are the one exception and they prove the point.** `mark-store.ts`
already persists per-document, per-page, region-and-text annotations with the
reader's own notes, across sessions, with staleness tracking against the file
stamp. It is the only durable, page-anchored, reader-authored structure in the
product. And the agent's entire access to it is a **count**: `ChatPanel.tsx:174`
passes `markCount`. The richest thing the reader makes is invisible to the agent
except as an integer.

This one ceiling is why each axis is stuck:

| axis | how the ceiling binds it |
|---|---|
| **Token cost** | The dominant cost is re-reading pages across turns. Compaction shrinks the transcript; it cannot stop the re-read, because nothing carries forward what the page *meant*. |
| **Session quality** | Codex and Cursor keep a working set — what has been established stays established. PageWise re-derives. That is the difference the 深度学习 axis is pointing at, and it is architectural, not stylistic. |
| **SDK depth** | The unused capability is not an exotic API. It is that tools are modelled as read-only when the SDK imposes no such thing. |
| **UI** | A chat transcript is the wrong primary artifact for reading a document. Polishing it cannot fix that, which is why nine defect fixes did not feel like 质变. |

## 3. Proposal: the reading record

**One durable, page-anchored structure per document, written by both the reader
and the agent, that persists across sessions and is the app's primary surface.**

Not a chat log with better styling. The transcript becomes secondary — a
scratchpad — and the record becomes the thing you keep.

### 3.1 The agent can write, not only read

Two new tools beside the six:

- `note_finding(page | pages, claim, evidence)` — records something established,
  anchored to the pages it came from.
- `revise_finding(id, claim, why)` — supersedes an earlier one when later
  reading contradicts it, keeping the old text and the reason.

These write into the same store marks already use, as a distinct kind. The
reader's marks and the agent's findings become one timeline over the document,
because they are the same kind of thing: *this passage means this*.

The revision half is not decoration. An agent that can only append accumulates
contradictions; one that must say what it is overturning and why produces a
record a reader can trust. This is also the honest answer to a real risk — see
§5.

### 3.2 The record is the context, instead of the pages

On each turn, the prefix carries the findings for the pages in play rather than
the pages themselves. A finding is a sentence; a page is ~6,000 characters.

The saving is structural, not a benchmark — **and I cannot measure it here.**
There is no live model in this environment, and two prior token estimates in
this project were wrong in exactly this way. What can be stated without a model
is the arithmetic already recorded in `compact-run-messages.ts`: a twenty-step
run over six-thousand-character pages moves ~1.26M characters, ~1.2M of which
are pages sent again. The record attacks the *second* copy of that problem — the
one compaction cannot reach, because it operates between turns rather than
within one.

The acceptance test must therefore be behavioural and local, not a token count:
**ask the same question twice, three turns apart, and the second run must not
re-read the pages the first one read.** That is checkable with the existing
harness and a faked provider, exactly as the citation defect was.

### 3.3 The record is the UI

This is where 质变 has to be visible or it did not happen.

- The right-hand column's default is the **record for the current page**, not
  the transcript. Turn to page 12 and you see what you and the agent have
  established about page 12 — the reader's marks, the agent's findings, the
  questions already answered there.
- Findings render **in the margin, anchored to their region**, in the same
  visual language marks already use. `PdfRect` and the region-mark renderer
  exist; this is a new consumer of a solved problem, not new geometry.
- The transcript is still there, one tab away. Asking a question is still the
  primary action. What changes is what the app shows you when you are not
  asking: the document, marked up with what is known about it.

## 4. Explicitly not proposed

Standing decisions, not re-litigated:

- **Semantic / embedding retrieval.** Rejected on record in
  `docs/reviews/2026-08-04-pagewise-v5.0-design.md` §6–§7, tried and reverted,
  and unmeasurable in this environment without an embeddings endpoint. The
  record improves recall by *remembering what was read*, which needs no
  embeddings and no new dependency.
- **Conversation branching.** Decided against ("不分叉"). The record is
  append-and-revise, not a tree; §3.1's revision is a single timeline.
- **Multi-document, office formats, encrypted PDFs, code signing.** Unchanged.
  The record is per-document precisely because the product is per-document.
- **`toolApproval`.** Stays as is. The new tools write to PageWise's own store,
  not to the filesystem or the network.

## 5. The risk, stated plainly

**A record of wrong findings is worse than no record**, because the agent will
trust it next turn and the reader will not know which sentence came from the
page and which from an earlier inference. This is the one way this proposal
fails badly, and it fails silently — the same shape as the page-citation defect
in 8.1.8, which sat inert between two sets of passing tests for the app's whole
life.

Three things follow, and they are requirements, not mitigations:

1. **A finding always carries its pages.** A finding with no anchor is not
   written. The reader can always get from a claim to the text it came from, in
   one click — the citation machinery for this now works (8.1.8).
2. **Findings are visibly the agent's, never the reader's.** Two authors, one
   timeline, never the same colour.
3. **The reader can strike one out**, and a struck finding never re-enters the
   context. Without this the reader cannot correct the agent's memory, and an
   uncorrectable memory is a liability.

## 6. Sequencing

Each step ships and is releasable on its own; each has an acceptance test that
fails before it.

- **9.0** — the store and the two tools. Findings persist, anchor to pages, show
  in the sidebar beside marks. *Acceptance: a finding survives a restart and
  points at its pages.*
- **9.1** — the record enters the prefix, pages leave it. *Acceptance: the
  same question three turns later re-reads nothing.*
- **9.2** — the record becomes the default surface; margin rendering; strike-out.
  *Acceptance: photographed at 900 / 1200 / 1440, both themes, by the harness
  that found the last nine defects.*

## 7. What I am not certain about

- Whether the agent, prompted to write findings, writes *useful* ones or
  narrates. This cannot be settled without a live model, and I will not claim it
  is settled. 9.0 is deliberately the cheapest step that makes it observable.
- Whether readers want a second surface at all, or just want the answer. The
  transcript staying one tab away is the hedge, and it is a real one.

## 8. Recommendation

Build 9.0. It is the only change on the table that moves all four standing axes
with one mechanism, it stays inside the fixed product positioning, and it
reuses the two structures the project already got right — marks, and the
page-anchored citation — rather than adding a dependency.

If only one thing is taken from this document: **the agent should be able to
write down what it learned.** Everything else follows from that.
