# 7.1 评估：会话每一轮都把上一轮的"思考"再买一遍，以及输入框有十五种

日期：2026-08-06 ｜ 基线：7.0.0（已发布）
实测编号接续 `2026-08-05-pagewise-v7.0-review.md`（V1–V69）。

---

## 0. 结论

7.0 把**一次运行之内**的重复发送修掉了。这一轮我沿着同一条链子往外走一层，看**跨轮次**还剩什么——结果是还剩两条，而且都比我预期的大：

1. **上一轮的推理内容，会随每一次新提问再发一遍。** `convertToModelMessages` 把持久化的 `reasoning` 片段还原成模型消息里的推理内容，而发送路径上没有任何地方剥掉它。开了思考的模型，第 N 轮要把前 N-1 轮的思考全部重付一次——**7.0 修掉的 N² 换了个维度又长回来了**。（前提要说清楚：`thinkingEnabled` 默认是关的，所以这条只咬那些开了思考、也正好最贵的用户。）
2. **整段会话没有任何窗口。** 工具结果被压缩了，但用户与助手的正文一条不落地全量重发，五十轮对话就是五十轮。

外加一条现在就在花钱的：**`search_in_document` 默认返回 50 条命中、每条约 240 字符 ≈ 1.3 万字符 ≈ 3300 token**，而模型通常看前十条就知道该读哪页了。

第 3 条（SDK）：**依赖已经全部是最新**（7.0 刚升过），所以这一轮的问题不是版本，是**装着却没用的能力**——其中 `toolApproval` 正好对着 PageWise 唯一一处真花钱的动作（视觉扫描）。

第 4 条（UI）：7.0 收敛了按钮。同样的病现在在输入框上——**15 条 CSS 规则各自完整定义了一遍"输入框长什么样"**。

## 1. token：跨轮次这一层 · V70–V73

### 1.1 上一轮的推理，每一轮都重买一次 · V70

```
ai/dist/index.js  convertToModelMessages:
  case "reasoning":  →  { type: "reasoning", text: part.text, providerOptions: … }

发送路径：useDocAgent → pagewise-chat-transport:84
  validateChatMessagesForSend(...)   ← grep "reasoning"：只在"判断这条消息是否为空"里出现
  convertToModelMessages(...)        ← 未传任何剔除选项
全仓库没有任何一处从发送内容中移除 reasoning 片段
```

推理内容是**按输出 token 计费产生的**，而它被存进会话、又在之后每一轮作为输入重新发送。开高档推理的模型一次思考几千 token 很常见——十轮之后，每次提问都要为前九轮的思考再付一次输入费。

**这条的前提我必须写明**：`DEFAULT_SETTINGS.thinkingEnabled = false`（`types.ts:127`），所以默认配置不受影响。它精确地命中"打开了思考的人"，而那正是单价最高的一批模型。

→ 修法：发送路径上剥掉 `reasoning` 片段（UI 与持久化照旧保留，折叠面板不受影响）。这是一个纯减法，且可以用"发送前后消息体积"直接测出来。

### 1.2 会话没有窗口，只有增长 · V71

全仓库找不到任何历史长度上限：`grep -n "MAX_MESSAGES|slice(-|historyLimit|maxTurns|trimHistory"` 只命中 `allowed-paths.ts` 的一个无关常量。

7.0 之后，历史里的**工具结果**已经被压成一行，但**用户提问与助手回答的正文**是全量的。一段长会话的输入会持续变大，直到撞上模型上下文上限——那时用户看到的是一次失败，而不是一次降级。

→ 修法：保留最近 N 轮原文，更早的轮次折叠成一句摘要（"前 12 轮：关于第 3–40 页的合同条款问答"），并在界面上明确显示"更早的对话已折叠"。**这一条我建议做得保守**：先只在超过阈值时折叠，且摘要由本地拼接产生、不额外调用模型。

### 1.3 一次搜索默认要 3300 token · V72

```
agent.ts:993   async ({ query, maxResults = 50 }, …)
document-search.ts:13   snippetAround(text, index, matchLen, radius = 120)  → 每条约 240 字符
50 × ≈260 字符 ≈ 13,000 字符 ≈ 3,300 token
```

而 7.0 的运行内压缩会**保留最近 4 条工具结果原样**——搜索通常就在最近这几条里，所以这 3300 token 会在后续每一步里跟着走。

→ 修法：默认 `maxResults` 50 → 12，`radius` 120 → 80（每条约 160 字符）。`maxResults` 参数本来就在（上限 200），需要更多时模型自己会要。粗算单次从 ≈3300 降到 ≈650 token。

### 1.4 视觉扫描这一条我查了，它是对的 · V73

```
index-queue.ts:180   renderPageToJpegBytes(path, page, 1568, 0.85)
```

1568 像素长边、JPEG 0.85 —— 正是主流视觉模型的推荐上限，再大不会更准，只会更贵。**这条不用改**，写在这里是因为你要求"每个环节"，而我确实查了。

## 2. 会话：7.0 之后还缺什么 · V74

7.0 加了步骤计数和可点击的步骤列表。对照 Codex / Cursor，还缺四件：

1. **仍然没有计划。** 步骤计数回答"第几步"，不回答"总共要做什么"。文档代理的计划是可以先写出来的：大纲 → 定位 → 读哪几段 → 综合。
2. **不能中途转向**，只能停。停了就得重问，前面读过的页也白读了。
3. **流式期间整个会话每个 chunk 重渲染一次。** `useChat` 没有传 `experimental_throttle`（`@ai-sdk/react` 提供，本仓库零使用），而每个 chunk 都会让 Markdown 重新解析。
4. **步骤没有耗时。** `stepUsage` 记了 token 不记时间，所以"卡住了还是在读一份大文件"分不出来。

→ 修法：`experimental_throttle` 一行就能上（先做）；步骤耗时是在 `onStepEnd` 里多记一个时间戳；计划视图需要模型配合，代价最大，排在最后；中途转向牵扯运行状态机，这一版仍然不做——我不想为了赶进度动那个机器。

## 3. SDK：版本已是最新，问题在没用的能力 · V75

```
ai 7.0.52 / @ai-sdk/react 4.0.55 / @ai-sdk/openai 4.0.30
pdfjs-dist 6.2.108 / lucide-react 1.28.0 / zod 4.4.3 / react-markdown 10.1.0   均为最新
react 19.2.7 → 19.2.8（一个补丁版）
```

装着但没用的：

| 能力 | 用它能解决什么 |
|---|---|
| `toolApproval` | **PageWise 唯一真花钱的动作是视觉扫描**。命令面板的批量扫描会弹确认，代理自己的按页扫描不会。这个能力就是为"执行前先问一句"准备的 |
| `experimental_throttle`（react） | §2.3 的流式重渲染 |
| 按步 `activeTools` | 读完之后就可以把 `document_outline` 关掉，减少每步的工具 schema |
| `toolOrder` | 影响模型的工具偏好，无需改提示词 |
| `resumeStream` | 崩溃/重启后接回未完成的流 |

→ 修法：这一版做 `experimental_throttle`（§2.3）与按步 `activeTools`（省 schema）。`toolApproval` 值得做，但它改变交互契约，我想单独一版认真做，并且要先问你：**你希望代理在扫描一页之前问你吗，还是维持现在"有配额、不打断"的做法？**

## 4. UI：按钮之后，轮到输入框 · V76

```
15 条 CSS 规则各自完整定义一遍输入框（同时含 border-radius + background/border）：
  .message-edit-input  .composer textarea   .settings-form input  .page-jump-input
  .zoom-select         .doc-search-input    .mark-note-input      .toolbar-page-input
  .settings-input      .settings-select-trigger  .model-select-badge
  .settings-row-toggle input[type=checkbox] …

面板 / 卡片 / 菜单 / 浮层类名：46 个
focus-visible 规则：12 条，散在 4 个文件
src/components/ui/ 下目前只有 Button
```

和按钮当初是同一个病：14 个 `<input>` 与 3 个 `<textarea>` 调用点，每一个的高度、内边距、聚焦态都是各写各的。

→ 修法：加两个原语——`Field`（label + input/textarea + 说明/错误）与 `Panel`（面板/卡片/浮层的外壳），把 15 条输入框规则和 46 个面板类名收敛过去。**和 7.0 一样只收敛外观、不动布局与类名语义**，分批提交。

同样的话第三次说：**jsdom 没有布局引擎，这部分最终要你在真机上看。**

## 5. 建议

**7.1 = §1.1 + §1.2 + §1.3（跨轮次的三条）+ §2.3/§2.4 + §3 的两项 + §4 的 Field/Panel。**

§1.1 是这一版最值钱的一条，也是最便宜的一条——一个纯减法。§1.2 我建议保守做。计划视图（§2.1）和 `toolApproval`（§3）各自需要一次单独的、认真的设计，我不想塞进这一版顺手做掉。
