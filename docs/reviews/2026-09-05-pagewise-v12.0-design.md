# PageWise 12.0 — 一次阅读，一份可带走的成果

*2026-09-05。基于对 v11.0.0（main `df2f6f8`）外部审查报告的复核而写。*

## 1. 对审查报告的评估

外部报告（`36319c1c-REVIEW.md`）给出七项发现（F1–F7）、一个产品判断和三个交付包。
本文档先回答一个问题：它说的对不对，哪些地方需要修正；再据此定 12.0 的范围。

### 1.1 七项发现逐条复核

| 编号 | 报告断言 | 复核结果 | 代码位置 |
|---|---|---|---|
| F1 | 过期或引文未匹配的记录仍以"已知事实"发给模型 | **成立。** `activeFindings` 只过滤 struck 与 superseded；`buildRecordInstructions` 不读 stamp、不读定位结果，且附带 "Treat these as known"。`findingsAreStale` 只用于面板横幅。 | `src/lib/finding-store.ts:266,289`、`src/lib/agent-record-context.ts:90-110` |
| F2 | 无法检查被误报为"文字不在引用页上" | **成立。** `pageRuns` 把 IPC 失败 catch 成 `[]`；`locateQuote` 在 `items.length === 0` 时返回 `absent`；UI 对 absent 显示 `record.notOnCitedPage`。扫描件、提取失败、断字换行三种情况与"原文确实没有"不可区分。 | `src/lib/finding-anchors.ts:53-60`、`src/lib/quote-locate.ts:106-108`、`src/components/RecordPanel.tsx:195` |
| F3 | 模型可保存越界页码 | **成立。** `note_finding` schema 只校验 `int().min(1)`；execute 拿到了 `doc` 却未按 `totalPages` 校验。`revise_finding` 同样。 | `src/lib/agent-tools/tools/note-finding.ts:33-36,49-56` |
| F4 | 保存答案静默截断并丢失格式 | **成立。** `claimFromAnswer` 整句截断分支不加省略号；`onKeep` 只传 `(claim, pages)`，不传来源 messageId；`RecordPanel` 用 `<p>` 直出。 | `src/lib/keep-answer.ts:26-32`、`src/components/MessageAssistantFooter.tsx:181`、`src/components/RecordPanel.tsx:182` |
| F5 | 记录不能独立导出 | **成立。** 四条导出路径（对话、摘要、文档、marks）均不序列化 findings。 | `src/lib/export-markdown.ts`、`src/lib/export-document.ts` |
| F6 | 连续性只到"最近文件" | **成立。** 打开即 `setPreviewPage(1)`；三个 store 都以绝对路径为键。 | `src/session/SessionProvider.tsx:332`、`src/chat/persist.ts:8`、`src/lib/recent-files.ts` |
| F7 | `{step}` 未插值 | **成立。** 两种语言都是单大括号，插值函数只认双大括号。 | `src/i18n/locales/*.json:264`、`src/i18n/index.tsx:46` |

复核中还发现一处报告没有点名、但直接决定 12.0 迁移方式的事实：
`finding-store.ts:156` 与 `mark-store.ts:139` 在 `parsed.version !== VERSION` 时**直接返回 `[]`**。
也就是说，今天任何一次 store 版本号提升都会静默清空用户的全部记录和批注。
报告写的"不可通过简单提升 store version 丢弃旧内容"不是谨慎措辞，而是对现有代码行为的准确预警。
12.0 必须先补迁移框架，再改数据结构。

### 1.2 报告的判断哪些成立

**"信任状态留在展示层"这一根因判断成立，而且比报告写的更集中。**
同一个 finding 至今有四个互不通信的信任信号：`struck`（用户）、`supersedes`（模型）、
`stamp`（文件）、`placement`（原文定位）。前两个进入模型上下文，后两个只进 UI。
F1、F2、F4 都是这一个裂缝的三个出口，不是三个独立 bug。

**"下一版不能再把增加记录包装为新方向"成立。**
9.0 设计的标题就是 *the document remembers*，10.0 做了引文定位，11.0 做了视觉规范。
记录这条线已经三个大版本，缺的不是功能，是"记下来的东西能不能被信任、能不能带走"。

**报告的边界意识值得保留。**
它明确区分了"代码确认"与"实测确认"，没有把三页占位文档的结果外推成长文准确率，
也没有从截图宣称可访问性结论。12.0 的验收沿用这一标准。

### 1.3 报告需要修正的地方

- **优先级排序应调整。** 报告把 A（可信证据）排第一。但 F4 的"保存即失真"是用户每次点击都会遇到的，
  F1 的"过期记录污染上下文"只在文件被替换后触发。用户可感知的顺序应当是：
  保存不失真 → 证据状态可信 → 能带走 → 能接着做。本文档按这个顺序排。
- **"Artifact 与 Finding 分离"的建议方向正确，但四个数据职责作为实现方案过重。**
  现有 `Finding` 加两个字段（`source`、`body`）加一个统一的信任状态派生函数，
  就能覆盖 F1/F4/F5 的需要，不必引入新的 store。12.0 用最小结构改动。
- **报告未给出"轻量入口"的验证方式。** "快速了解 / 核验一个问题 / 整理阅读简报"三个入口
  是合理猜想，但 9.2 设计已经指出本仓库没有可用的真实模型环境来验证模型行为。
  12.0 把入口作为可选项列入，不作为发布门槛。
- **F7 不应等到 12.0。** 一行文案修复，应作为 11.0.1 立即发布。

## 2. 12.0 的目标

**一位读者打开一份长文档，问几个问题，把答案里值得留的部分留下，第二天打开还在原处，
最后导出一份不需要看聊天记录也能读懂、每条结论都能回到原文的简报。**

这句话是 12.0 的验收单位。它涉及的四段路径今天各断一处：

| 路径 | 今天断在哪 | 12.0 之后 |
|---|---|---|
| 留下答案 | 500 字符、丢格式、丢来源 | 完整正文与结论分开存，格式保留，可回到原答案 |
| 信任记录 | 四个信号各说各的 | 一个状态，UI、模型上下文、导出三处一致 |
| 带走成果 | 只能导出对话 | 导出简报：结论 / 依据 / 待确认，每条带页码 |
| 接着做 | 回到第 1 页，改名即失联 | 恢复位置，文件身份与路径分离 |

不做的事见第 6 节。

## 3. 数据模型：最小改动

### 3.1 Finding 加两个可选字段

```ts
interface Finding {
  // ...现有字段不变
  /** 完整正文（Markdown）。只有 reader 通过"留下"写入时才有。claim 是它的摘要。 */
  body?: string;
  /** 来源回答的 messageId。有它才能"回到原回答"。 */
  source?: { messageId: string };
}
```

`claim` 继续做列表摘要与模型上下文用的一句话；`body` 是导出和展开阅读用的全文。
两者的关系是"摘要 / 正文"，不再是"截断 / 丢弃"。

### 3.2 一个派生的信任状态

```ts
type Trust =
  | "confirmed"    // reader 人工确认
  | "located"      // 引文已在文档当前版本定位
  | "unverified"   // 引文太短或没有引文（今天的 uncheckable）
  | "unlocated"    // 有引文，可提取文本中找不到；可能是断字、可能是扫描件
  | "unreadable"   // 该页没有文字层或提取失败，无法检查
  | "stale"        // 文件已变，尚未复核
  | "retracted";   // struck 或 superseded
```

`trustOf(finding, doc, placement): Trust` 是**唯一**的计算入口。
三处消费者全部改成读它：

- `RecordPanel` 按 Trust 显示状态行与可用操作；
- `buildRecordInstructions` 只把 `confirmed | located | unverified` 当作"已知"，
  `stale | unlocated | unreadable` 以"待复核，引用前请重读该页"的措辞附上，`retracted` 不发；
- 导出按 Trust 分组到"结论 / 依据 / 待确认事项"。

新增 `confirmedAt?: number` 字段承载人工确认；`stale` 与 `unreadable` 由运行时派生，不落盘。

### 3.3 Placement 补两个状态

`FindingPlacement` 从三态扩到五态：`located | absent | uncheckable | unreadable | unlocated`。
`pageRuns` 不再把失败折成空数组，而是返回 `{ items, reason: "ok" | "no-text-layer" | "failed" }`。
`locateQuote` 保持纯函数，由 `finding-anchors` 根据 reason 决定是 `unreadable` 还是 `absent`。
`absent` 仅在"该页有文字层且字符串确实不在其中"时出现，且 UI 文案改为
"未在该页可提取文本中定位"，附"查看该页"与"我已核对"两个操作。

### 3.4 迁移框架（前置，阻塞其他所有项）

三个 store（findings、marks、chats）统一走 `migrate(parsed): Stored` 链，
`version` 只能前进，未知版本**保留原文件并复制一份 `*.bak`** 后再尝试解析，绝不返回 `[]`。
为 findings 加 `version: 2 → 3` 的迁移用例，验证 9.x 写入的旧数据完整进入新结构。

## 4. 交付包与顺序

### 包 0 · 立即发布 11.0.1

- F7：`stepCounter` 改为 `{{step}}`；加测试遍历两个 locale，凡含单大括号占位符即失败。
- F3：`note_finding` 与 `revise_finding` 在 execute 层校验 `pages ⊆ [1, doc.totalPages]`，
  越界返回 `{ recorded: false, reason: "page N is out of range 1–M" }`；
  加载时越界的历史记录标为 `retracted` 并保留，不删除。

两项都是一两个文件的改动，不必等 12.0。

### 包 1 · 留下的东西不失真（F4）

- `onKeep` 传 `(claim, pages, { body: markdown, messageId })`。
- `claimFromAnswer` 整句截断分支补省略号，并加测试。
- `RecordPanel` 有 `body` 的条目默认折叠显示 claim，展开渲染 Markdown（复用聊天已有的渲染器）。
- 条目有 `source` 时显示"回到原回答"，点击滚动到该消息并高亮。
- 允许读者编辑 `claim`（不编辑 `body`），编辑后自动 `confirmedAt`。

### 包 2 · 一个信任状态（F1、F2）

- 按 3.2、3.3 实现 `Trust` 与五态 `Placement`。
- `buildRecordInstructions` 改造，并加请求审计用例：
  更新同路径文件后，实际发出的记录注释中过期条目不得出现在 "Treat these as known" 段落。
- `RecordPanel` 每条显示 Trust 图标与一行文案；`unlocated | unreadable | stale` 提供"我已核对"。
- 引文匹配增加断字换行折叠（`-\n` → 空），现有 hyphen 用例从"报告 unlocated"改为"定位成功"。

### 包 3 · 带得走的简报（F5）

- 新增 `findingsToMarkdown(doc, findings, trust)`：
  标题、文档名、文件 stamp 与页数；三节：结论（confirmed/located）、依据（每条引文与页码）、
  待确认事项（stale/unlocated/unreadable/unverified）；retracted 不出现。
- 加入"更多操作"菜单为"导出简报"，与"导出对话"并列。
- 简报中的页码用 9.4 引入的印刷页码，括注 sheet 序号。

### 包 4 · 接着做（F6）

- `LoadedDocument` 加 `identity`：内容指纹（首 64 KB + 尾 64 KB + size 的 hash），Rust 端计算。
- 三个 store 的键从 `path` 改为 `identity`，迁移时用现有 path 反查一次指纹并写入。
- 打开文档时若 path 无记录但 identity 有，直接接管并更新 path。
- `recent.json` 每条加 `lastPage`、`lastScroll`、`findingCount`、`openQuestions`（unverified 数量）。
- 打开时恢复到 `lastPage`；文档库每行显示"读到第 N 页 · 结论 K 条 · 待确认 J 条"。

### 可选 · 首次打开的三个入口

"快速了解 / 核验一个问题 / 整理阅读简报"作为空对话状态的三个示例问题变体加入，
只影响预填文案，不新增工具，不改变模型行为。不进入验收门槛。

## 5. 验收

沿用报告第七节，改为可在本仓库执行的形式：

1. **保存不失真（自动化）**：含表格、加粗、末尾限制条件的 2,000 字答案，留下后重开，
   `body` 逐字相等，`claim` 以省略号结尾，`source.messageId` 可解析。
2. **信任一致（自动化，请求审计）**：改写文件 stamp 后发起问题，
   捕获实际请求，过期条目出现在"待复核"段而非"已知"段；struck 条目不出现。
3. **证据边界（自动化）**：文字页、扫描页（无文字层）、IPC 失败、断字换行四组 fixture，
   分别得到 `located / unreadable / unreadable / located`，任何一组返回 `absent` 即失败。
4. **越界拒绝（自动化）**：3 页文档 `note_finding({pages:[999]})` 返回 `recorded:false`。
5. **迁移不丢数据（自动化）**：9.x 格式的 findings/marks/chats fixture 升级后条目数不变，且生成 `.bak`。
6. **连续工作（手动，UI harness）**：读到第 37 页关闭再打开，落在第 37 页；
   改名后打开，记录与对话完整；替换文件内容后，旧条目显示 stale。
7. **简报可读（手动）**：不打开应用，仅读导出的 Markdown，能说出每条结论在哪一页、哪些待确认。

**主指标**：一名首次使用者用样本文档在 5 分钟内完成"提问 → 留下 → 导出简报"，
且导出文件中每条结论都能在应用内回跳到页面。11.0 基线中这条路径在"留下"一步失真、在"导出"一步不存在。

## 6. 这版不做

| 候选 | 判断 |
|---|---|
| 更多模型供应商 | 与本版目标无关。 |
| 跨文档知识库、两份文档对照 | 需要 identity 与 Trust 先落地；作为 13.0 第一个候选。 |
| 视觉重做 | 11.0 的状态规范保留，12.0 只新增 Trust 行、展开正文、简报菜单三处 UI。 |
| 自动 OCR 扫描件以修复 unreadable | 会在用户未授权时把整页图像发给视觉模型。12.0 只标状态并给"识别此页"手动入口。 |
| 多 Agent、插件 | 无证据表明本条路径需要。 |
| 安装签名 | 发行门槛，不是产品价值；另行安排。 |

## 7. 实施记录（同日）

12.0.0 按第 4 节的顺序实现，与方案的出入如下：

- **包 0 的 11.0.1 未单独发布。** 用户直接要求发布 12.0，三项改动随 12.0 一并交付。占位符问题实际是每种语言各 11 处（`marks.*` 也用了单大括号），不止 `stepCounter` 一处。
- **迁移框架用 `<key>.newer` 槽位代替 `.bak` 文件。** Tauri store 是一个 JSON 文件内的键值，没有"复制一份文件"的原语；来自更高版本的 blob 保存在同一 store 的旁路键下，且不覆盖已有槽位。较低版本的 blob 按迁移链升级。两个 store 从 1 升到 2 作为证明。
- **确认动作会把条目的 stamp 更新到当前文件版本。** 否则对"过期"条目点"我已核对"没有可见效果。设计稿 3.2 的 Trust 规则不变。
- **对话的文件身份用 store 内索引键 `pagewise:identity-index`**，而不是改主键。
- **进度只到页，不到页内滚动位置。** 与第 6 节一致。
- **未做的可选项**：首次打开的三个入口。
- **Rust 侧只做了独立函数验证**（`file_identity` 在临时 crate 中编译并跑过同内容不同路径、尾部改动、空文件三种情况）；本环境缺少 GTK 依赖，`cargo check` 整体无法在本地完成，交由 CI 的 `rust` job。

## 8. 风险

- **迁移是唯一不可逆的一步。** 包 4 改 store 键之前，包 0 的迁移框架和 `.bak` 必须先合入并发布一版。
- **Trust 状态会让记录面板首次出现大量"待确认"。** 这是把已存在的不确定性显示出来，不是回归；
  发布说明要写清楚。
- **模型对"待复核"措辞的实际反应无法在本仓库验证。** 与 9.2 的处境相同，只能通过请求审计保证
  发出去的内容正确，不能保证模型据此行为正确。
