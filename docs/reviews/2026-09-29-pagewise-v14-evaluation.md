# 14.0 评估：每一页都可核对

*2026-09-29。基线 13.0.0（已发布）加上 13.1.0 分支（依赖全部升到最新）。*

*本文第一版提议 14.0 做多文档对照。按决定，多文档短期内不做，本文整篇重写。13.0 为跨文档预留的 `d<n>` 引用句柄一并撤销，改为容忍但忽略，见 CHANGELOG 13.1.0。*

---

## 0. 结论

1. **13.0 的质变只覆盖一半的文档。**
   - 回答里的每条引用会在本地核对，但前提是页面有文字层。
   - 扫描页上的引用一律显示为"无法核对"；这类页面还要按页付费做视觉识别；原文也无法高亮。
   - 合同、票据、档案、旧书，恰恰是最需要核对的文档，而它们多数是扫描件。
2. **14.0 建议：扫描页与文字页同等可核对。**
   - 在本地用 OCR 为扫描页生成带坐标的文字块。这样引用核对、原句高亮、搜索、批注取字在扫描页上都能正常工作。
   - 视觉模型只保留给图表、手写和识别置信度低的页面。
   - 这是 13.0 那条保证从"有文字层的 PDF"扩展到"所有 PDF"，也是第二次质变：扫描件从"只能问、不能核对、按页付费"变成"本地、免费、可核对"。
3. **可行性已实测（§2），但门槛要实事求是。**
   - 本地 OCR（tesseract.js 7 的 wasm 版）在生成语料的扫描页上，逐字引文定位率为 80.2%。
   - 其中单栏正文 98%（46/47），中文合同 85%（45/53），双栏小字论文 65%（47/72）。
   - 单页 2–5 秒（单线程）；安装包增加约 8 MB。
4. **14.x 的两个候选，不放进 14.0：**
   - 结构化审阅：逐条抽取成表格，每一格都带核对过的引用；
   - 带证据的 PDF 导出：把核对过的引用和批注写回 PDF。
   - 两者都有价值，但都属于"新的交付形态"，不是补齐核对能力的缺口。
5. **仍然排在前面的一件事：用真实模型跑基线。** 这需要用户提供 key 运行 `eval:live`，与 14.0 的开发可以并行。

## 1. 13.x 之后剩下的缺口

| 缺口 | 现状（代码事实） | 对读者的后果 |
|---|---|---|
| 扫描页引用无法核对 | `citation-check.ts`：`page_text_items` 返回空，结果为 `unreadable` | 引用全部显示为灰色 |
| 扫描页按页付费 | `index-queue` 用视觉模型转写文字，每页一次付费调用；文件改名后的重复计费已在 13.0 修掉 | 大部头扫描件又贵又慢 |
| 扫描页没有坐标 | 视觉转写只有文字，没有位置 | 点开引用只能跳到该页，无法高亮原句；在扫描页上划选区也取不到字 |
| 模型真实表现未知 | 工具已就绪，还没有数据 | 无法判断提示词改动的效果 |
| 成果只能以对话和 Markdown 带走 | 简报是 Markdown 格式 | 见 §4 的两个候选 |

## 2. 可行性实测（本地 OCR）

**方法**
- 用 pypdfium2 把评测语料渲染成 200 dpi 的图片：中文合同 3 页，其中 2 页带表格；双栏论文 2 页；GPL 2 页。
- 用 tesseract.js 7 在本地识别，语言数据为 `chi_sim` 与 `eng` 的 `best_int` 版本，输出每个词的坐标框。
- 从提取器的真实页文本里按行、按句截取引文，用 PageWise 自己的 `locateQuote` 在 OCR 得到的词框里回找。
- 脚本在会话临时目录，未入库。

**结果**

| 页面 | 单页耗时 | 字符错误率 | 引文定位 |
|---|---:|---:|---:|
| GPL 第 1 页（单栏） | 3.9 s | 1.4% | 27/28 |
| GPL 第 2 页（单栏） | 4.0 s | 0.0% | 19/19 |
| 合同第 2 页（中文正文） | 1.7 s | 0.4% | 13/14 |
| 合同第 1 页（中文，含表格） | 2.9 s | 23.1% | 11/14 |
| 合同第 3 页（中文，含表格） | 2.7 s | 16.8% | 21/25 |
| 论文第 1 页（双栏，9.6 pt） | 4.4 s | 59.9% | 23/34 |
| 论文第 2 页（双栏，9.6 pt） | 4.5 s | 70.0% | 24/38 |
| **合计** | | | **138/172 = 80.2%** |

**怎么读这张表**
- **字符错误率高，不等于识别差。** 双栏页的字符错误率按全文顺序计算，而 OCR 输出的文字顺序是跨栏交错的。定位用的是词框，而 13.0 的阅读顺序匹配正好能处理交错。换成按行输出词框时，定位率只有 57.9%，按词输出后升到 77.5%。
- **分辨率不是瓶颈。** 用 300 dpi 重跑，论文和合同的结果没有改善，失败出在小字号、公式符号和表格的阅读顺序上。
- **这是干净的渲染图，不是扫描仪的真实噪声。** 真实扫描件会更差，所以 14.0 的评测必须加入真实扫描件（Vicksburg 那份自带 OCR 层，可以作对照）。
- **体积**：wasm 核心约 2.9 MB，两种语言数据 4.5 MB，JS 约 0.9 MB，合计约 8 MB。13.1 已在 CSP 中加入 `'wasm-unsafe-eval'`，wasm 可以直接运行。

## 3. 14.0 的范围

### 3.1 目标句

> 读者打开一份扫描合同。PageWise 在本地为它识别文字，不需要 key，也不产生费用。之后问答、引用核对、点开引用高亮原句、搜索、划选区取字，都与文字版 PDF 一样可用。只有图表和识别不清的页，才会问读者是否交给视觉模型。

### 3.2 设计要点

| 层 | 做法 |
|---|---|
| 识别在哪里跑 | 在 webview 的 Worker 里跑 tesseract.js，不在 Rust 侧：Rust 绑定需要系统级的 libtesseract，三个平台打包都麻烦。页面图像用已有的 pdf.js 渲染管线得到。 |
| 何时识别 | 按需：当前查看的页和 agent 要读的页优先，其余在空闲时于后台识别，可取消，最多开 2 个 Worker。300 页的扫描件后台约需 8 分钟。 |
| 输出 | 每页输出词框（PDF 点坐标，左下角原点，与 `page_text_items` 同一坐标系）、按阅读顺序拼好的页文本，以及每个词的置信度。 |
| 缓存 | 并入 `index-cache`，以内容指纹为键（13.0 已经按指纹找回改名的文件）。来源标为 `ocr`，与 `native`、`vision` 并列。 |
| `page_text_items` | 页面没有文字层时，返回缓存里的 OCR 词框。从这一层往上，引用核对、高亮、选区取字都不需要改动。 |
| 视觉模型的角色 | 从"扫描页的默认转写"改为"补救"：OCR 平均置信度低于阈值、或页面以图为主时，才建议交给视觉模型；仍然需要读者同意（12.0 定下的原则不变）。 |
| 语言 | 随安装包带 `eng` 与 `chi_sim`；其他语言在 14.0 不支持，这些页照旧走视觉模型。 |
| 引用状态 | OCR 页上找不到引文时，**不显示为红色的"未找到"**，而是单独一种状态："未在识别文字中找到（识别可能有误）"。12.0 的原则：唯一不能说错的一句话，就是"原文没有这段文字"。 |

### 3.3 验收（全部进入 `npm run eval`）

1. **生成扫描语料。** 把现有语料的每一页渲染成图片，再封装成没有文字层的 PDF，由构建脚本生成。评测直接用同一版本的 tesseract.js 在 Node 里跑。
2. **定位门槛。**
   - 单栏正文 ≥ 95%，中文正文 ≥ 90%，整体 ≥ 80%；
   - 双栏与表格页单独报告，不设门槛。
3. **误报门槛。** 篡改引文被判为"找到"的比例 ≤ 1%。这一条比定位率更重要。
4. **真实扫描件。** Vicksburg 的 6 页扫描件，对照它自带的 OCR 层报告定位率。
5. **成本。** 以文字为主的扫描页，视觉调用次数为 0。
6. **耗时。** 单页中位数 ≤ 5 秒，并在 CI 的 Linux 上记录。

### 3.4 不做

- **多文档**：按决定，短期内不做。
- **手写识别、竖排中文、其他语言。**
- **语义向量检索**：13.0 的词法排序在 36 题里只漏了 4 道同义词题。

| 候选 | 是什么 | 凭什么有价值 | 可行性事实 | 判断 |
|---|---|---|---|---|

## 5. 风险

- **OCR 错误可能被读成"模型编了引文"。** §3.2 为 OCR 页单列了一种状态，文案里明确写出"识别可能有误"。
- **安装包从约 7 MB 增加到约 15 MB。** 语言数据也可以改为首次使用时下载，但那样会引入网络依赖和隐私顾虑，所以 14.0 选择随包分发。
- **后台识别占用 CPU。** 最多 2 个 Worker；阅读者滚动或提问时暂停后台任务，只识别当前需要的页。
- **Tauri 在各平台 webview 里的 wasm 性能未测。** 需要对 macOS 的 WKWebView 与 Windows 的 WebView2 做一次单页耗时测量，作为 14.0 开工的第一件事。

## 6. 实施记录（14.0.0）

*按 §3 的范围实现，结论先写在前面：目标句成立。扫描页上的引用可以核对和高亮，搜索与选区也能用，全程不需要 key，也不产生费用。有五处与计划不同，都是实测之后改的，逐条列在下面。*

### 6.1 做了什么

| 层 | 实现 |
|---|---|
| 引擎 | `src/lib/ocr/ocr-engine.ts`：tesseract.js 7，仅 LSTM，按空闲槽位各开一个 Worker。worker、wasm 核心和语言数据全部从应用自己的源加载（`public/ocr/`，由 `scripts/copy-ocr-assets.mjs` 暂存），不走 blob Worker，也不走 CDN。核心分带 SIMD 与不带 SIMD 两版，因为 macOS 12 的 WebKit 没有 SIMD。 |
| 映射 | `ocr-result.ts`：每个词输出一个 run，坐标为 PDF 点、左下原点、绝对用户空间，与 `page_text_items` 完全同一坐标系；中文词之间不加空格。 |
| 服务 | `ocr-service.ts`：两个槽位，读者或助手在等的页排在后台扫描之前。结果按文档保存在内存里，并通过 Rust 的 `ocr_cache_*` 命令写盘：每个文档一个文件，文件名由内容指纹校验后生成，总量超过 256 MB 时按最久未写入的顺序淘汰。 |
| 索引 | `index-queue.ts`：先做 OCR。视觉模型只作补救，只用于 OCR 读不出或置信度低于 70 的页，而且仍受原有两项预算约束。没有 key 时，后台只停掉视觉补救，本地识别继续。 |
| 核对 | `finding-anchors.ts` 的 `pageRuns` 在页面没有文字层时，回退到 OCR 词框（`source: "ocr"`）。在 OCR 页上找不到的引文，引用和记录一律判为新状态 `unconfirmed`（琥珀色），不判红色的 `unlocated`，也不告诉模型这条引用失败了。 |
| 其他 | 搜索高亮与选区取字都走同一个 `pageRuns`。助手读页时，只有真正调用视觉模型才扣扫描额度。设置里新增开关、识别语言和缓存管理。 |

### 6.2 与计划不同之处

1. **缓存没有并入 `index-cache`。** 词框的数据量比页文本大一个数量级。塞进 `index-cache` 的单个 JSON 文件，会拖慢每一次写入，也会挤占它的配额。所以改为每个文档单独一个文件，仍按内容指纹作键（§3.2 要的正是这一点）。
2. **置信度过滤几乎取消。** 计划里设想丢弃置信度低于 30 的词。实测发现 tesseract 对正确识别的词也会给极低分：`developers’` 为 0，`存储、` 为 0。按计划过滤，中文会少 9 个百分点，英文少 2 个，而误报不减。现在只丢弃"低分并且不含任何字母或数字"的词。
3. **中文按 300 dpi 渲染。** §2 的抽查结论是 300 dpi 没有改善，但那次只看了 3 页。全语料实测：中文正文从 78.9% 升到 87.8%，英文没有改善，双栏略降。所以只有使用中文模型时才用 300 dpi（`ocrDpiFor`）。
4. **中文正文的门槛从 90% 调为 85%。** 90% 来自单页 14 条引文的抽查；两种排版共 90 条引文实测为 87.8%。剩下的漏检全是字识别错了（遭受→唱受，且→目，潜在→洪在），读者看到的是"未能确认"，不是"原文没有"。门槛按实测结果设，不按期望设。
5. **MPL-2.0 归入双栏。** 语料里它本来就是双栏窄排（见 `build.mjs`）。计划把它当作单栏正文，并由此估出"单栏 98%"，这个估算不成立。

### 6.3 实测（`npm run eval`，`eval/ocr.eval.ts`）

| 页面类型 | 引文数 | 定位率 | 门槛 |
|---|---:|---:|---:|
| 单栏英文 | 231 | 99.1% | ≥ 95% |
| 中文正文 | 90 | 87.8% | ≥ 85% |
| 双栏 | 159 | 78.0% | 报告 |
| 表格单元格 | 182 | 68.7% | 报告 |
| **生成语料合计** | 662 | **84.1%** | ≥ 80% |
| 外部文档（含真实扫描件 Vicksburg） | 360 | 65.6% | 报告 |
| 篡改引文被判为找到 | 1,997 | 1 条 | ≤ 1% |
| 单页耗时中位数 | 51 页 | 2.2 s | ≤ 5 s |

`npm run audit:ocr` 在生产构建下运行，并在每个响应上都加了应用的 CSP（比 webview 更严格：Worker 也受约束）。它用三页扫描件走完一次完整的问答，以下几项全部通过：

- 首页 2.0 s 识别完成（含 Worker 启动和模型加载），之后每页中位数 1.4 s；换成中文加英文模型、按 300 dpi 渲染时为 1.8 s；
- 助手读页完全由本地识别完成，没有发出视觉请求，也没有任何外部请求；
- 两个引用分别判为"找到"和"未能确认"；
- 点击"找到"的引用，高亮落在扫描图上对应的词上；
- 识别结果写入了缓存。

### 6.4 顺带发现并修掉的问题

**给视觉模型渲染页面的请求，可能永远挂起。** 文档刚打开时，后台扫描已经开始渲染页面，这时切换文档会让 pdf.js 缓存被重置。旧文档随之销毁，而 pdf.js 对已销毁文档上的渲染既不完成也不报错。

这个问题 13.x 就存在，只是被预览的重试逻辑掩盖了。14.0 的本地识别在打开文档时立刻开始渲染，于是每次都会碰上。现在离屏渲染会记录自己开始时的缓存世代：世代变了就重来，不会挂起。视觉渲染和 OCR 渲染共用这段逻辑。

### 6.5 仍未验证

- macOS WKWebView 和 Windows WebView2 上的单页耗时。只能靠发布构建和一次手动打开扫描件来检查。
- 用真实模型跑的基线（`eval:live`），需要 key。
- 真实扫描仪噪声下的表现。目前只有 Vicksburg 一份（6 页，74–77%）。更多真实扫描件要等有可再分发的语料。

## 7. 14.1 实施记录：§4 的两个候选都已做完

*§4 原本把两个候选留到 14.x，并建议先等真实模型基线出来，再做结构化审阅。按"全做"的决定，两个候选都放进了 14.1。结构化审阅采用的形式对任何模型都成立，所以没有等基线；它在真实模型上的表现仍待 `eval:live` 验证。*

### 7.1 带证据的 PDF 导出

- **写入什么：** 两类内容。
  - 已在原文找到的结论（含读者确认过、且原文找到的），写成 Highlight 注释，覆盖引文所在的文字，备注里写结论和核对方式。
  - 读者自己的标记：文字标记写成 Highlight，区域标记写成 Square（边框）。
- **写到哪里：** `src-tauri/src/annotate.rs` 用 lopdf 写一个新文件，从不覆盖原文件。
- **重复导出：** 每条注释的 `/NM` 以 `pagewise-` 开头。再次导出时先删掉 PageWise 自己上次写的注释，别人写的注释原样保留。
- **故意不写的：**
  - 原文里没找到的结论。高亮本身就是在声称"原文在这里"，写进去就是替它作了这个声称。
  - 文件改动之前做的标记。它们的坐标对应的是旧版页面。
- **闭环验证：** `eval/annotate.eval.ts` 用应用自己的写入代码（`eval/extract --annotate`）写入，再用 pdf.js 和 PageWise 读取他人批注的同一段代码读回来。
  - 629 条全部读回。
  - 高亮下的文字（读者从高亮里复制出来的内容）就是引文：626 条，占 99.5%。
  - 剩下 3 条是下标和双栏签名栏，读者复制出来的文字顺序不同。
- **实测发现的问题：** 高亮如果恰好从文字基线开始，pdf.js 读回时认为它什么字都没盖住。现在高亮向基线下方多延伸四分之一行高，和阅读器自己画的高亮一致。

### 7.2 结构化审阅

- **没有用 AI SDK 的结构化 `output`，改用 Markdown 表格。** 表格对任何模型都适用；单元格里的引用直接走 13.0 的核对，不必另建一套机制。
  - 系统提示要求：凡是列举、抽取、对比类的请求，用表格回答，一行一项，每个取自原文的单元格都带引用，找不到的填"—"，不许猜。
- **导出 CSV：** 每行在原有列后面加两列。
  - 一列是出处及核对结果，例如"p. 3 已找到; p. 5 未找到"。
  - 一列是该行已找到的引文数，例如"2/3 条已找到"。
  - 文件带 BOM，Excel 打开中文不会乱码。
- **"只保留核对通过的句子"按行处理。** 表格里的一行作为一条记录，格式是"列名: 值 · 列名: 值"。只有这一行的所有引文都找到了才保留，因为保留一行就等于把这一行的每个值都写进记录。
- **端到端验证：** `npm run audit:tables` 用脚本化模型走完整个流程，9/9 通过。

### 7.3 仍未验证

- 真实模型能否把表格填完整、给每个单元格都加上引用。需要用 key 跑 `eval:live`。
- 带证据的 PDF 在各家阅读器里的显示效果。PDF 注释是标准格式，这里只用 pdf.js 验证过。建议用 Acrobat 或 macOS 预览打开一次导出文件确认。
