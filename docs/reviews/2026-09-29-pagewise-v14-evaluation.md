# 14.0 评估：每一页都可核对

*2026-09-29。基线 13.0.0（已发布）加上 13.1.0 分支（依赖全部升到最新）。*

*本文第一版提议 14.0 做多文档对照。按决定，多文档短期内不做，本文整篇重写。13.0 为跨文档预留的 `d<n>` 引用句柄一并撤销，改为容忍但忽略，见 CHANGELOG 13.1.0。*

---

## 0. 结论

1. **13.0 的质变只覆盖一半的文档。**
   - 回答里的每条引用会在本地核对，但前提是页面有文字层。
   - 扫描页上的引用一律显示为"无法核对"；这类页面还要按页付费做视觉识别；原文也无法高亮。
   - 合同、票据、档案、旧书，恰恰是最需要核对的文档，而它们多数是扫描件。
2. **14.0 建议：扫描页与文字页同等可核对。**
   - 在本地用 OCR 为扫描页生成带坐标的文字块。这样引用核对、原句高亮、搜索、批注取字在扫描页上都能正常工作。
   - 视觉模型只保留给图表、手写和识别置信度低的页面。
   - 这是 13.0 那条保证从"有文字层的 PDF"扩展到"所有 PDF"，也是第二次质变：扫描件从"只能问、不能核对、按页付费"变成"本地、免费、可核对"。
3. **可行性已实测（§2），但门槛要实事求是。**
   - 本地 OCR（tesseract.js 7 的 wasm 版）在生成语料的扫描页上，逐字引文定位率为 80.2%。
   - 其中单栏正文 98%（46/47），中文合同 85%（45/53），双栏小字论文 65%（47/72）。
   - 单页 2–5 秒（单线程）；安装包增加约 8 MB。
4. **14.x 的两个候选，不放进 14.0：**
   - 结构化审阅：逐条抽取成表格，每一格都带核对过的引用；
   - 带证据的 PDF 导出：把核对过的引用和批注写回 PDF。
   - 两者都有价值，但都属于"新的交付形态"，不是补齐核对能力的缺口。
5. **仍然排在前面的一件事：用真实模型跑基线。** 这需要用户提供 key 运行 `eval:live`，与 14.0 的开发可以并行。

## 1. 13.x 之后剩下的缺口

| 缺口 | 现状（代码事实） | 对读者的后果 |
|---|---|---|
| 扫描页引用无法核对 | `citation-check.ts`：`page_text_items` 返回空，结果为 `unreadable` | 引用全部显示为灰色 |
| 扫描页按页付费 | `index-queue` 用视觉模型转写文字，每页一次付费调用；文件改名后的重复计费已在 13.0 修掉 | 大部头扫描件又贵又慢 |
| 扫描页没有坐标 | 视觉转写只有文字，没有位置 | 点开引用只能跳到该页，无法高亮原句；在扫描页上划选区也取不到字 |
| 模型真实表现未知 | 工具已就绪，还没有数据 | 无法判断提示词改动的效果 |
| 成果只能以对话和 Markdown 带走 | 简报是 Markdown 格式 | 见 §4 的两个候选 |

## 2. 可行性实测（本地 OCR）

**方法**
- 用 pypdfium2 把评测语料渲染成 200 dpi 的图片：中文合同 3 页，其中 2 页带表格；双栏论文 2 页；GPL 2 页。
- 用 tesseract.js 7 在本地识别，语言数据为 `chi_sim` 与 `eng` 的 `best_int` 版本，输出每个词的坐标框。
- 从提取器的真实页文本里按行、按句截取引文，用 PageWise 自己的 `locateQuote` 在 OCR 得到的词框里回找。
- 脚本在会话临时目录，未入库。

**结果**

| 页面 | 单页耗时 | 字符错误率 | 引文定位 |
|---|---:|---:|---:|
| GPL 第 1 页（单栏） | 3.9 s | 1.4% | 27/28 |
| GPL 第 2 页（单栏） | 4.0 s | 0.0% | 19/19 |
| 合同第 2 页（中文正文） | 1.7 s | 0.4% | 13/14 |
| 合同第 1 页（中文，含表格） | 2.9 s | 23.1% | 11/14 |
| 合同第 3 页（中文，含表格） | 2.7 s | 16.8% | 21/25 |
| 论文第 1 页（双栏，9.6 pt） | 4.4 s | 59.9% | 23/34 |
| 论文第 2 页（双栏，9.6 pt） | 4.5 s | 70.0% | 24/38 |
| **合计** | | | **138/172 = 80.2%** |

**怎么读这张表**
- **字符错误率高，不等于识别差。** 双栏页的字符错误率按全文顺序计算，而 OCR 输出的文字顺序是跨栏交错的。定位用的是词框，而 13.0 的阅读顺序匹配正好能处理交错。换成按行输出词框时，定位率只有 57.9%，按词输出后升到 77.5%。
- **分辨率不是瓶颈。** 用 300 dpi 重跑，论文和合同的结果没有改善，失败出在小字号、公式符号和表格的阅读顺序上。
- **这是干净的渲染图，不是扫描仪的真实噪声。** 真实扫描件会更差，所以 14.0 的评测必须加入真实扫描件（Vicksburg 那份自带 OCR 层，可以作对照）。
- **体积**：wasm 核心约 2.9 MB，两种语言数据 4.5 MB，JS 约 0.9 MB，合计约 8 MB。13.1 已在 CSP 中加入 `'wasm-unsafe-eval'`，wasm 可以直接运行。

## 3. 14.0 的范围

### 3.1 目标句

> 读者打开一份扫描合同。PageWise 在本地为它识别文字，不需要 key，也不产生费用。之后问答、引用核对、点开引用高亮原句、搜索、划选区取字，都与文字版 PDF 一样可用。只有图表和识别不清的页，才会问读者是否交给视觉模型。

### 3.2 设计要点

| 层 | 做法 |
|---|---|
| 识别在哪里跑 | 在 webview 的 Worker 里跑 tesseract.js，不在 Rust 侧：Rust 绑定需要系统级的 libtesseract，三个平台打包都麻烦。页面图像用已有的 pdf.js 渲染管线得到。 |
| 何时识别 | 按需：当前查看的页和 agent 要读的页优先，其余在空闲时于后台识别，可取消，最多开 2 个 Worker。300 页的扫描件后台约需 8 分钟。 |
| 输出 | 每页输出词框（PDF 点坐标，左下角原点，与 `page_text_items` 同一坐标系）、按阅读顺序拼好的页文本，以及每个词的置信度。 |
| 缓存 | 并入 `index-cache`，以内容指纹为键（13.0 已经按指纹找回改名的文件）。来源标为 `ocr`，与 `native`、`vision` 并列。 |
| `page_text_items` | 页面没有文字层时，返回缓存里的 OCR 词框。从这一层往上，引用核对、高亮、选区取字都不需要改动。 |
| 视觉模型的角色 | 从"扫描页的默认转写"改为"补救"：OCR 平均置信度低于阈值、或页面以图为主时，才建议交给视觉模型；仍然需要读者同意（12.0 定下的原则不变）。 |
| 语言 | 随安装包带 `eng` 与 `chi_sim`；其他语言在 14.0 不支持，这些页照旧走视觉模型。 |
| 引用状态 | OCR 页上找不到引文时，**不显示为红色的"未找到"**，而是单独一种状态："未在识别文字中找到（识别可能有误）"。12.0 的原则：唯一不能说错的一句话，就是"原文没有这段文字"。 |

### 3.3 验收（全部进入 `npm run eval`）

1. **生成扫描语料。** 把现有语料的每一页渲染成图片，再封装成没有文字层的 PDF，由构建脚本生成。评测直接用同一版本的 tesseract.js 在 Node 里跑。
2. **定位门槛。**
   - 单栏正文 ≥ 95%，中文正文 ≥ 90%，整体 ≥ 80%；
   - 双栏与表格页单独报告，不设门槛。
3. **误报门槛。** 篡改引文被判为"找到"的比例 ≤ 1%。这一条比定位率更重要。
4. **真实扫描件。** Vicksburg 的 6 页扫描件，对照它自带的 OCR 层报告定位率。
5. **成本。** 以文字为主的扫描页，视觉调用次数为 0。
6. **耗时。** 单页中位数 ≤ 5 秒，并在 CI 的 Linux 上记录。

### 3.4 不做

- **多文档**：按决定，短期内不做。
- **手写识别、竖排中文、其他语言。**
- **语义向量检索**：13.0 的词法排序在 36 题里只漏了 4 道同义词题。

## 4. 14.x 候选（评估后留待之后）

| 候选 | 是什么 | 凭什么有价值 | 可行性事实 | 判断 |
|---|---|---|---|---|
| 结构化审阅 | "列出合同所有付款条件和违约金"之类的请求，产出一张表，每一格都带核对过的引用，可导出 CSV | 从零散的问答变成系统的、可审计的抽取 | AI SDK 7 的 `ToolLoopAgent` 支持结构化 `output`，最后一步可以边生成边输出（13.1 调研确认） | 14.x 首选。等真实模型基线出来后，先量一下模型能否稳定填好表格 |
| 带证据的 PDF 导出 | 把核对过的引用和读者批注，写成 PDF 里的高亮和注释 | 对方不装 PageWise，也能在自己的阅读器里看到证据 | 13.1 已直接依赖 lopdf，可以写 Highlight 注释（QuadPoints）加弹出注释；写回后还能用 PageWise 自己读注释的代码回读验证，形成闭环 | 14.x 第二候选 |
| 主张与证据的支持关系核对 | 引文确实在页上，但它能不能支撑这条结论 | 从"引文存在"升级为"引文成立" | 需要额外的模型调用，本地无法完成 | 真实模型基线出来后再议 |

## 5. 风险

- **OCR 错误可能被读成"模型编了引文"。** §3.2 为 OCR 页单列了一种状态，文案里明确写出"识别可能有误"。
- **安装包从约 7 MB 增加到约 15 MB。** 语言数据也可以改为首次使用时下载，但那样会引入网络依赖和隐私顾虑，所以 14.0 选择随包分发。
- **后台识别占用 CPU。** 最多 2 个 Worker；阅读者滚动或提问时暂停后台任务，只识别当前需要的页。
- **Tauri 在各平台 webview 里的 wasm 性能未测。** 需要对 macOS 的 WKWebView 与 Windows 的 WebView2 做一次单页耗时测量，作为 14.0 开工的第一件事。
