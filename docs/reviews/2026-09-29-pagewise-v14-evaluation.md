# 14.0 评估：从"一份可核对的文档"到"一组可核对的文档"

*2026-09-29。基线 13.0.0（已发布，`de3df18`）加上 13.1.0 的依赖升级（本分支）。与依赖调研同步完成；依赖部分的结论见 §4。*

---

## 0. 结论

1. **13.0 的质变已经落地，但只覆盖"有文字层的 PDF"。**
   - 扫描页上的引用一律是 `unreadable`，也就是"无法核对"。
   - 回答里有 `〔…〕` 标记之后，引用能不能被核对，取决于页面是否有文字层。
2. **14.0 建议：多文档对照，并支持跨文档引用。**
   - 引用格式已经预留了文档句柄 `d<n>`。
   - 13.0 的核对管线按"文档 + 页"缓存，结构上能直接扩展到多文档。
   - 能力从"读一份"变成"比对一组"，这是第二次质变。
3. **进入 14.0 之前要先补两件事，排在 13.x：**
   - **真实模型基线。** 13.0 还没有任何真实模型的数据，`eval:live` 需要用户的 key 才能跑。多文档会让提示词更长、引用更复杂，没有基线就无法判断改动是变好还是变坏。
   - **扫描页引用可核对。** 视觉识别得到的文字已经缓存在本地，引用可以对这段文字做文本级核对，结果单列一种状态："在识别文字中找到"。这样 13.0 的保证就能覆盖扫描件。
4. **不建议 14.0 做语义向量检索。** 13.0 的词法排序在 36 题里只漏了 4 题，而且全是同义词问题。为这 4 题引入本地向量模型或外发 embedding，成本和隐私代价都不相称。可以先加一张同义词表，在评测里量一下效果。

## 2. 14.0 的范围

### 2.1 目标句

> 读者打开两份合同，问"两份的违约责任有什么不同"。回答中每条事实都带有 `〔d1 p5 "…"〕` 或 `〔d2 p7 "…"〕` 这样的引用，分别在各自的文档上核对。点开引用会切换到对应的文档和页，并高亮原句。

### 2.2 必须改的地方

这些位置取自 13.0 复查时的代码盘点，行号以 13.0 为准：

| 层 | 现状 | 14.0 |
|---|---|---|
| `doc-cache` | `MAX_CACHED_DOCS = 1`，切换文档时整套拆除 | 工作集最多 N 份（先定 4 份），用 LRU 淘汰 |
| `pdf.ts` | 只有一个 pdf.js 句柄 | 每份文档一个句柄，预览区只渲染当前那份 |
| `SessionProvider` | `document` 是单值，切换即拆除 | 改为 `workset` 加 `activeDoc`，切换不拆除 |
| 工具 | 8 个工具里 5 个不接受 `path` 参数 | 统一加可选的 `doc: "d2"` 参数，省略时用当前文档；工具定义的摘要会变，付出一次缓存失效 |
| 系统提示 | "The user has one active PDF" | 列出工作集中各文档的句柄与名称，这部分放在易变上下文里 |
| 引用 | 已预留 `d<n>`，解析后被忽略 | `CitationLink` 加 `doc` 字段，核对和高亮都按文档进行 |
| 对话键 | 以单个文档的 path 为键 | 工作集对话单独存储，键为文档身份的有序组合 |
| 记录 | 按文档分开存 | 仍按文档分开存；跨文档结论记在引用的每一份文档下 |
| 评测 | 只有单文档题目 | 增加对照题：同一合同的两个版本（生成语料里再造一份改过条款的合同），检查答案里的引用是否指向正确的文档 |

### 2.3 不做

- **跨文档知识库或全库检索。** 工作集由读者显式打开，不做后台索引。
- **自动选文档。** 模型只能引用工作集里已有的文档。

## 3. 13.x 的前置工作（按顺序）

1. **13.1（本分支）：依赖全部升到最新，并用上新能力。** 详见 §4 和 CHANGELOG。
2. **真实模型基线：**
   - 用户用 `npm run eval:live` 至少跑一个工具能力强的模型，把录制结果提交到 `eval/baselines/`。
   - 作为 14.0 的对照线：引用覆盖率、定位率、页码命中率、平均步数。
3. **13.2：扫描页引用可核对。**
   - 视觉识别的文字已按页缓存，缓存键是 `path + stamp` 或内容指纹。
   - 引用落在扫描页时，改为在识别文字里做折叠后的子串匹配。
   - 找到时，状态为"在识别文字中找到"：比 `located` 弱，因为没有坐标可以高亮；比 `unreadable` 强。
   - 页面高亮退化为整页高亮。
   - 评测加一个扫描件题组（Vicksburg 已有 OCR 层，可以作为对照）。

## 5. 风险

- **多文档会放大 token 成本。**
  - 每份文档的记录注释和页码标签提示都会进入易变上下文。
  - 需要一个工作集级的总预算：记录部分总共 2,000 字符，按文档平分。
- **引用写错文档句柄。** `d1`、`d2` 容易写反。核对是按句柄在对应文档上查的，写错时会显示为"未找到"而不是误判为"找到"，这本身就是核对管线的价值。评测里加一类"句柄写反"的篡改用例，确认它会被拒绝。
- **依赖升级的平台风险。**
  - Tauri 2.12 在 macOS 和 Windows 上的行为只能由 release 构建和人工冒烟测试来验证。
  - 本地和 CI 能跑的只有 Linux 上的 `cargo test`，已经通过。
