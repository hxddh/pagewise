# 7.0 评估：一次提问最多要重发 31 万 token，而缓存从来没命中过

日期：2026-08-05 ｜ 基线：6.3.0（已发布）
实测编号接续 `2026-08-05-pagewise-v6.3-review.md`（V1–V61）。

---

## 0. 结论

你点了四件事，我按四条各挖了一轮。**最重的发现全在第 2 条（token）**，而且不是"再省一点"的量级：

1. **同一次提问内，每一步都把之前所有工具结果原样重发。** 20 步的问答，最坏情况一次请求链累计 **≈31.5 万 input token**——其中 30 万是同一批页面文本被重复计费。装着的 SDK **本来就支持修**（`prepareStep` 可以返回改写后的 `messages`），我们没用。
2. **系统提示里带着"用户正在看第 N 页"**，于是读者一翻页，整段会话的前缀缓存就全部失效——每一轮都按全价重新计费整个历史。而 usage 里**根本没有记录 cached token**，所以这件事一直没人看得见。
3. `document_outline` 一个结果最多 **≈4 万字符 ≈1 万 token**（200 页 × 160 字预览），然后被上面第 1 条乘以步数。

第 1、3 两条相乘，就是你感觉到的"仍然存在大量浪费"。

第 3 条（SDK 版本）也确实落后：`ai` 装的是 **7.0.14，最新 7.0.52**，中间有 45 条实质变更，其中一条正好是我们需要的能力。

第 1 条（会话质量）我要说句公道话：**它没有你想的那么糟**——工具步骤有折叠、推理有折叠、"读过的页"可点击跳转、用量有弹窗、可编辑重发、可中止。缺的是**过程的可读性**，不是过程本身。

第 4 条（UI）在 6.3 之后，问题已经从"值不统一"变成"**没有组件层**"：21 个不同的按钮类名，没有一个共享的按钮组件。

## 1. token：链条上每一环 · V62–V66

### 1.1 同一次运行内，工具结果按步数重复计费（最严重）· V62

跨轮次的裁剪做得很好——`pruneToolOutputsForHistory` 会把上一轮的页面文本换成 `[Read page 12, 5,800 chars — omitted]`。**但它只在 `onFinish` 时执行**（`useDocAgent.ts:224`），也就是说：

**一次运行之内，第 N 步会把第 1…N-1 步的完整工具结果全部重发。**

```
DEFAULT_PAGE_MAX_CHARS = 6_000     每页最多 6000 字符
DEFAULT_MAX_AGENT_STEPS = 20       每次提问最多 20 步
RUN_CHAR_BUDGET = 200_000          一次运行最多读 20 万字符

第 20 步携带：      20 × 6,000 = 120,000 字符 ≈ 30,000 token
整轮累计 input：  Σ(i×6,000)   = 1,260,000 字符 ≈ 315,000 token
其中约 30 万是重复内容
```

**这不是无解的**——装着的 SDK 明确支持：

```ts
// node_modules/ai/dist/index.d.ts
/**
 * The messages that will be sent to the model for the current step.
 * If you return a `messages` override, those messages carry forward to later steps.
 */
```

而我们的 `prepareStep` 只设了 `toolChoice`，代码注释里还专门写着"never mutates messages"——当时是为了安全，但代价是这个。

→ 修法：在 `prepareStep` 里对**两步以前**的读取类工具结果做与跨轮相同的压缩（`[Read page 12, 5,800 chars]`）。最近一到两步保持原样，模型正在用它们；更早的页面文本如果还需要，可以再读一次，而缓存里本来就有，重读不花钱。预计把一次 20 步运行的 input 从 ≈31.5 万降到 **≈5 万 token 量级**。

### 1.2 前缀缓存从未命中，而且没人看得见 · V63

```ts
instructions: SYSTEM_INSTRUCTIONS + viewHint
```

`viewHint` 来自 `buildViewContextInstructions`：

```
Active document: "报告.pdf" (312 pages, file: "/…/报告.pdf").
The user is viewing page 47; read that page first for "this page"…
```

系统消息是整个请求的**第一条**。OpenAI / OpenRouter 的自动缓存按前缀精确匹配——**系统提示变一个字，整段会话的缓存全废**。而"正在看第几页"在一个阅读工具里几乎每一轮都不同。

代价不是这 1.5KB，是**每一轮都按全价重算整个历史**（缓存命中通常只收 10% 的价）。

更糟的是它无法被观测：`message-metadata.ts` 记了 `inputTokens` / `outputTokens` / `stepUsage`，**没有 `cachedInputTokens`**。用量弹窗里也就没有这一行。

→ 修法两步：
1. 系统提示恢复成**逐字节恒定**，把"正在看第 N 页 / 文档名 / 总页数"移到**当前这条用户消息**里（位置在最后，不影响前缀）；
2. `cachedInputTokens` 记进 metadata 并在用量弹窗里显示——**修完要能看见修好了**。

### 1.3 `document_outline` 一次最多一万 token · V64

```ts
const MAX_OUTLINE_PAGE_STATS = 200;
const allStats = pages.map((p) => ({ page, chars, preview: p.text.trim().slice(0, 160) }));
```

200 条 × 约 200 字符 JSON ≈ **4 万字符 ≈ 1 万 token**，一个工具结果。代码注释里已经承认"每条约 200 字符"，但只加了上限、没有减重。

而广义问题通常**第一步就调它**，于是这 1 万 token 会被 §1.1 乘以剩下的步数。

→ 修法：预览从 160 字降到 60 字（够判断这页讲什么），并且**默认只回目录树 + 页字符数**，逐页预览改成按需（`detail: "previews"` 参数）。粗算单次从 ≈1 万降到 ≈2 千 token。

### 1.4 推理档位对 20 个步骤一视同仁 · V65

```ts
export function resolveReasoning(settings) {
  if (!settings.thinkingEnabled) return undefined;
  return isBigModel ? "high" : "medium";
}
```

一次运行里，"再调一次 read_pdf_page"和"综合 12 页写出答案"用的是**同一个推理档位**。推理 token 是计费的输出 token，而机械的取数步骤不需要思考。

→ 修法：`prepareStep` 里按步分档——中间步骤降到 `low`/关闭，最后的综合步骤恢复 `high`。7.0.42 的 `60f97f6: support overriding model call settings for individual prepareStep invocations` 正是为此，而我们装的 7.0.14 **没有这个能力**（见 §3）。

### 1.5 没有任何输出上限 · V66

全仓库 `maxOutputTokens` 零命中。一次跑飞的生成没有任何天花板——既是钱，也是延迟。

→ 修法：设一个宽松但存在的上限。

## 2. 会话：它比你想的好，缺的是"过程可读" · V67

先把已经有的说清楚，免得重做：

| 已有 | 位置 |
|---|---|
| 工具步骤折叠 + 运行中/失败状态点 | `MessageContent.tsx:100` |
| 推理过程折叠 | `MessageContent.tsx:240` |
| **"读过的页"可点击跳转** | `PagesReadTrail` |
| 用量弹窗（输入/输出/扫描调用数，代理与索引分开） | `MessageAssistantFooter.tsx:160` |
| 编辑并重发、重新生成、中止 | `ChatPanel.tsx:453/604` |
| 网页搜索来源链接 | `collectSources` |

缺的是这些（对照 Codex / Cursor）：

1. **20 步的过程压缩成了一行。** 折叠标题是"读取了 6 处"这类聚合，展开是纯文本列表 `<li>{label}</li>`——**不可点击、无耗时、无页码链接**，而同一个消息里的 `PagesReadTrail` 却是可点的。同一份信息，两种待遇。
2. **没有计划。** Codex 会先给出待办再逐条勾掉；这里 20 步之间用户看到的只有一句会变的"正在扫描文档…"。文档代理的计划天然存在（大纲 → 定位 → 读 → 综合），只是没显示。
3. **缓存与成本不可见**（§1.2）。
4. **不能中途转向**，只能停。停了就得重问。

→ 修法（按性价比排序）：
- 把工具步骤列表变成**带页码链接、带耗时的时间线**，复用 `PagesReadTrail` 已有的跳转；
- 运行中在消息顶部显示**当前计划与进度**（"第 3/6 步：读第 40–52 页"），数据 `stepUsage` 里已经有；
- 用量弹窗补 cached 一行；
- 中途转向留到之后，它牵扯运行状态机。

## 3. SDK：落后 38 个补丁版，且缺的正是我们要用的能力 · V68

```
ai                7.0.14  →  7.0.52   （45 条实质变更）
@ai-sdk/react     4.0.15  →  4.0.55
@ai-sdk/openai     4.0.7  →  4.0.30
pdfjs-dist      6.1.200  →  6.2.108
lucide-react     1.23.0  →  1.28.0
zod / react-markdown / react            已是最新
```

`^` 允许升级，但锁文件把它钉在 7.0.14，所以**发出去的包一直是旧的**。

与我们直接相关的几条：

| 版本 | 变更 | 为什么相关 |
|---|---|---|
| 7.0.42 | `support overriding model call settings for individual prepareStep invocations` | §1.4 分档推理**依赖它** |
| 7.0.33 | `preserve tool parts when tool call IDs repeat across steps` | 我们一次运行 20 步，正是重复调用同一工具的场景 |
| 7.0.29 | `Allow validating assistant UI messages with empty parts so persisted errored responses remain loadable` | 我们持久化会话，出错的回复目前可能加载不回来 |
| 7.0.30 | `Fix chat onFinish handling when overlapping requests…` | 快速连发两条消息的路径 |
| 7.0.24 | `repairToolCall` 转正 | 我们还在用 `experimental_` 前缀 |

**已装 SDK 里没用上的能力**（不必升级就能用）：`prepareStep` 的 `messages` 覆写（§1.1）、按步 `activeTools`（读完就可以关掉 outline 工具）、`toolOrder`。

→ 修法：升级五个包到最新，补 `experimental_` → 正式名，然后做 §1.1/§1.4。升级要单独一个提交，便于出问题时回退。

## 4. UI：值统一了，组件还没有 · V69

6.3 把 193 处 px 字号收进了 token。剩下的问题变了性质：

```
不同的按钮类名（*btn*）        21 个
共享 UI 原语目录 src/components/ui   不存在
顶层组件                       27 个
```

`toolbar-btn` / `link-btn` / `stop-btn` / `mark-ask-btn` / `preview-index-retry-btn` / `library-remove` …每一个都是一套独立的 padding、高度、hover、focus。**这就是"粗糙"的来源**：不是某个按钮丑，是没有两个按钮真正一样。

→ 修法：建立最小组件层——`Button`（primary / secondary / ghost / icon 四种，尺寸两档）、`Field`、`Panel`、`Menu`——然后把 21 个类名逐个换过去。**这一步不改任何布局，只把重复的按钮定义收敛成一个**，可以分批提交、逐屏验证。

同样的话我在 6.3 说过、这次仍然成立：**jsdom 测不了布局，这部分最终要你在真机上看。**

## 5. 建议

**7.0 = §3（升级）→ §1.1 + §1.2（token 止血）→ §1.3/§1.4/§1.5 → §2（过程可读）→ §4（组件层）。**

顺序是有依赖的：§1.4 需要 §3 升级后的能力；§2 的"缓存可见"需要 §1.2 先记录。

体量上这是一个大版本。§1.1 和 §1.2 两条如果单独发，本身就值一个版本——**它们直接减掉的是你每一次提问的账单**，而且我可以用 `stepUsage` 把前后对比测出来给你看。
